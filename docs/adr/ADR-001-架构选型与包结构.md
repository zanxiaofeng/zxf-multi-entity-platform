## 1. 背景与约束

本仓库是单代码库多实体部署骨架：共享内核不分叉，差异代码进独立 SPI 模块，构建期经 Maven profile 按实体裁剪产出互不背书的二进制。五个 Maven 模块（`platform-core` / `entity-alpha` / `entity-beta` / `platform-flowable-starter` / `app`）已按设计文档第五章落地并配有 Enforcer + ArchUnit 护栏。

本 ADR 的目的：① 用选型指南的统一术语为仓库整体及各模块定级；② 登记三处对标准布局的有意偏差；③ 记录三项子决策（实体模块分包、domain 分包粒度、查询侧演进触发），作为后续评审与演进的依据。

硬约束（既定，不在本 ADR 重新决策）：依赖单向 `entity-* → platform-core`、`app → platform-core`（Enforcer）；三开关成对（构建 profile ↔ `SPRING_PROFILES_ACTIVE` ↔ `platform.entity`）；差异一律走 `PricingPolicy` 式扩展点 + `@ForEntity` 限定。

## 2. 决策

### 2.1 总体组合

**E 模块化单体（按实体维度裁配的变体）× C 组合（A.4 DDD 四层·依赖倒置版 + 六边形端口）+ 第 7 章 Outbox 局部启用。**

决策路径（选型指南 1.1）：

| 问题 | 回答 | 结论 |
| --- | --- | --- |
| Q1 规则密集核心域？ | 计价/审批/风控规则存在，但核心诉求是多实体差异注入，需要抽象与依赖隔离 | 候选 C |
| Q2 读写差异明显？ | 查询仅 `GET /orders/{id}`，无报表/复杂列表 | 不引入 B |
| Q3 D 的收益证据？ | 无投影、无独立读存储；Outbox 已有——指南 2.2 明确「事件驱动可单独用于 C，并非 D 专属」 | 维持 C，局部启用第 7 章 |
| Q4 可识别模块边界？ | 内核 / 实体 SPI / 装配，且为 Maven 物理边界 | 叠加 E |
| Q5 独立部署收益超分布式成本？ | 产物按实体裁剪，但每产物内部仍是完整单体，非按限界上下文拆服务 | 维持单体 |

结构洞察：**整个仓库是放大版六边形**——`app`（bootstrap 最外圈，装配可见全部端口与实现，指南 4.4）→ `entity-*`（外圈：端口的适配器实现，`@ForEntity` 限定）→ `platform-core`（内圈：端口契约 + 用例 + 领域模型）。Maven 单向依赖 `entity-* → platform-core` 即「外圈依赖内圈」的编译期表达；Enforcer + ArchUnit + 装配矩阵是 E 模块化单体的物理边界守护形态（强于指南 A.7 的包边界）。

### 2.2 逐模块选型

| 模块 | 选型定级 | 说明 |
| --- | --- | --- |
| `platform-core` | **C 组合**：A.4 DDD 四层（依赖倒置版）为骨架，融合六边形端口归属（指南 4.4）、Pipe-Filter（2.3，`OrderPipeline`：纯契约骨架在 `domain.port`，编排与阶段实现在 application / 实体模块）、工作流（Flowable，`infrastructure.engine` 引擎适配层）、Outbox（第 7 章 / EVT-002） | 仓储接口在 `domain.port`、实现在 `infrastructure.persistence`（指南 4.4 认可的端口归属）；读写同路径（无 CQRS）；协作 = 进程内领域事件 + `AFTER_COMMIT` + Outbox |
| `entity-alpha` / `entity-beta` | **六边形出站适配器模块**（SEL-001 最小组合） | 端口的适配器实现（SPI），不承载独立业务上下文，非 A.7 意义上的业务模块（无 api/internal 双面）。扁平 `adapter` 包 + `@ForEntity` + ArchUnit 守护 |
| `platform-flowable-starter` | **技术装配组件**（指南 6.3 装配惯例） | 纯 Spring Boot starter：单根包 + `@AutoConfiguration` + `Properties` + `Detector` + `HealthIndicator`，经 imports 文件注册而非组件扫描。扁平单包即终点形态，不参与业务分层 |
| `app` | **bootstrap 装配模块**（A.3/A.4 的 `bootstrap` 独立成 Maven 模块） | profile 裁剪、产物名带实体标识、三开关 fail-fast；同时承担测试金字塔尖（指南第 11/12 章）：E2E、装配冒烟（= 12.1 最小 Spring 上下文验证）、漂移负例 |

### 2.3 已登记偏差（GOV-002：有意取舍，非技术债）

| # | 偏差 | 理由与替代保护 |
| --- | --- | --- |
| 1 | `core.context` 是对 A.4 的扩展层（指南无对应）：多实体上下文横切（`EntityContext` ThreadLocal、`@ForEntity`、`AsyncConfig` 传播） | 平台特有横切无处安放；ArchUnit 白名单实质即给该包签发「框架耦合登记例外」（ARC-002 例外条款）。约束：`EntityContext` 仅限同步 Servlet 栈，引入 WebFlux 需架构评审（README Review 硬性规则 7） |
| 2 | core 无 `port.in`（UseCase 接口），`interfaces.rest` 直调 `OrderApplicationService` 类 | A.4 DDD 四层风格（interfaces 委派 AppService），与 `.claude/rules/architecture.md` 的六边形 `port.in` 风格并存——PKG-001 允许模块异构但需可解释：**core 维持 A.4 风格，后续新增业务模块遵循 rules 的六边形规范，两套命名不得在同一模块内混用** |
| 3 | 测试用每类独立 H2 库，非生产同语义真实库（TEST-002 例外） | demo 定位有意选型（生产 Oracle + 测试 H2，ACT_* 为 H2 方言脚本）；已登记于 CLAUDE.md「骨架适用范围」。退出条件：接入真实业务模块、转生产化时切换 Testcontainers 并重提取 ACT_* 方言脚本 |

### 2.4 子决策

**D1 — 实体模块分包（已决策：维持扁平）**
实体模块维持扁平 `adapter` 包（当前 alpha/beta 各 6 类，指南 6.1「小模块不必为了分包而拆散几行逻辑」）。约定触发阈值：**单实体 `adapter` 类数超过约 12–15，或出现第二种职责族时**，按扩展点类型分子包（`adapter/{pricing,pipeline,process,document,capability}` 式），分拆属纯移动不改行为。

**D2 — `domain` 分包粒度（已决策：维持按类型，不做迁移约定）**
`domain.{model,service,event,port,exception}` 按类型分包。指南 A.4 与 rules 规范按聚合分包（`domain/order/`），单聚合（Order）下两者等价。决策：**维持现状，不预设「第二聚合出现即迁移」的约定**；若未来因规则散落重评（见复审触发），按指南 3.1「A/B→C」路径整体重议，而非仅动分包。

**D3 — 查询侧演进（仅记录触发条件，当前不动作）**
不建 `application.query`、不引入 View 层。触发条件（指南 3.1 A→B）：查询模型拖累写服务、报表 SQL 频繁变化。触发后最小迁移范围：先拆一个查询服务与输出模型，保持写路径，对比延迟与结果正确性后切回决策。

## 3. 候选方案与不选原因

| 候选 | 不选原因 |
| --- | --- |
| B 分层 + 轻量 CQRS | 查询极简，双路径无收益（代码路径翻倍的纯成本） |
| D 全配置（投影/独立读存储） | 无读扩展、检索能力或隔离需求的证据；运维成本（投影滞后、重建、契约演进）无对价 |
| 微服务 | 多实体 ≠ 多服务：实体差异是装配期裁剪，非运行期独立伸缩/演进诉求；无分布式运维准备 |
| 垂直切片 | 本项目差异维度是「实体」而非「用例」，切片与 SPI 模块正交且无叠加必要 |
| Clean/Onion 命名体系 | 与六边形同族（指南 2.4）；A.4 命名已选，不在同一仓库无说明地引入第二套重叠命名 |

## 4. 保证与非保证

**保证**：
- 编译期依赖单向（Enforcer）；领域核心包零实体/框架感知（ArchUnit）；差异实现全部 `@ForEntity` 元注解限定（含 `@Bean` 工厂绕过面）。
- 事务内副作用经领域事件 + `AFTER_COMMIT`，跨边界发布意图与业务同事务持久化（Outbox，EVT-002）。
- 装配正确性由三防线兜底：启动期 `PolicyRegistry` fail-fast → CI 装配矩阵 → `/actuator/info` 实体巡检。

**非保证**：
- 无读写分离（当前读己之写直读权威库，天然满足；引入异步读模型后须按 CQRS-002 定义新鲜度契约）。
- 无跨进程一致性诉求（单体）；`EntityContext` 不覆盖响应式栈。
- H2 测试不证明 Oracle 锁与方言行为（偏差 3 的既有边界）。

| 选型指南规则 | 本仓库守护 | 强度 |
| --- | --- | --- |
| PKG-002 边界不依赖内部实现 | Maven Enforcer（依赖单向、实体互禁、双 profile 拒绝） | 物理边界，强于指南示例 |

回退/演进均按指南 3.1 触发表执行（按问题迁移，不按等级升级），本 ADR 不预设迁移步骤。

## 6. 复审触发

- **查询复杂度**：报表/列表拖累写服务 → 按 D3 触发条件重评 B 式读写分离。
- **规则散落**：相同业务约束散落多处、状态变更难测试 → 重议 domain 分包粒度（D2）与领域建模深度。
- **读扩展压力**：读压垮写库、下游解耦诉求出现 → 评估 D 的部分机制（先增一个投影，非全套）。
- **实体协作升级**：实体间出现进程外协作或独立伸缩诉求 → 评估拆服务（届时 E 的物理边界即拆分资本）。
- **规范基线变化**：选型指南或 `.claude/rules` 更新与本 ADR 冲突时。
