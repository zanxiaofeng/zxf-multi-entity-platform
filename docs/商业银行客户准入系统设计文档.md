# 商业银行客户准入（Customer Onboarding）系统设计文档——基于 Flowable 流程引擎

版本 V1.0 | 日期 2026-09-23 | 读者对象：银行科技部门架构师与开发团队

## 1. 概述与技术选型

## 1.1 业务背景与设计目标

### 1.1.1 商业银行客户准入的业务链路

客户准入（Customer Onboarding）是银行与客户建立业务关系的第一道关口，本质是一条跨渠道、跨部门、跨系统的长链路核验与审批流程。典型企业客户准入链路为：**渠道受理**（柜面/线上提交申请与影像）→**KYC 尽调**（采集身份、经营与受益所有人信息）→**名单筛查**（反洗钱名单模糊匹配与人工甄别）→**风险评级**（划分审批层级，高风险触发加强尽调）→**审批**→**开户**→**签约**→**归档**（资料按新《反洗钱法》留存 10 年[^1^]）。监管对若干环节设有明确时限与人工责任要求（详见第 2 章），准入链路因此不能简化为一次同步交易，必须作为状态可持久化、责任可追溯的流程来管理。

### 1.1.2 业务特征决定流程引擎适配性

该链路呈现五项业务特征，逐项对应引擎能力域：

表 1-1 业务特征与流程引擎能力域映射

| 业务特征 | 技术平台要求 | 引擎能力域 |
|---|---|---|
| 长周期（含等待补件，可达数日） | 状态持久化、挂起恢复、催办 | 实例持久化、定时边界事件 |
| 人机混合（尽调、甄别、审批须人工负责） | 人机任务混合编排 | 用户任务、异步服务任务、候选组 |
| 强合规审计（还原操作责任人与依据） | 全程留痕、历史可查 | HistoryService、审计级历史 |
| 多渠道复用（柜面/线上共用准入逻辑） | 流程与渠道解耦 | 引擎嵌入后端、REST/服务 API |
| 规则高频变更（监管换版带动评级调整） | 规则与骨架分离 | DMN 决策表外置规则 |

前四项特征指向"需要一台流程引擎"而非状态机硬编码；第五项进一步要求规则外置能力。准入流程骨架相对稳定，而评级规则、名单处置、审批路由随监管换版高频调整，两者必须分离管理——这是采用 BPMN 2.0 + DMN 双引擎路线的根本原因。

### 1.1.3 设计目标

本设计确立四项目标，后续各章决策均以可回溯到这些目标为合格标准：**流程平台化**——准入流程以独立流程服务承载，渠道经 API 轻接入；**规则外置化**——三类规则（风险评级、审批路由、资料清单模板）外置到 DMN 决策表，名单命中处置结论并入评级决策表的首行规则（命中即拒绝），由合规人员维护；**操作语义化**——驳回、加签、转办、委派等操作由平台层封装为语义接口；**全程可审计**——每次状态变迁留责任人、时间戳与依据，审计流水独立于引擎历史表另建归档层，满足 10 年留存要求[^1^]。

## 1.2 技术选型决策

### 1.2.1 候选方案对比

引擎选型有三条现实路径：开源 Flowable 自研扩展、商业 BPM 采购、Camunda 体系（7 或 8）：

表 1-2 流程引擎候选方案对比

| 对比维度 | Flowable 开源路线 | 商业 BPM 采购 | Camunda 7 | Camunda 8（Zeebe） |
|---|---|---|---|---|
| 架构形态 | 嵌入式 Java 引擎 + 关系库，Spring Boot 原生集成 [^2^] | 厂商套件私有化部署 | 与 Flowable 同构 [^2^] | 分片+Raft、无关系库、仅远程、最终一致 [^3^] |
| 生命周期与许可证 | Apache 2.0，最新主版本 8.0.0（2026 年 2 月）[^4^] | 商业许可，演进由厂商主导 | 社区版已 EOL（2025-10）[^5^][^6^] | 非 OSI 许可证，社区版不可免费生产使用 [^2^][^7^] |
| 信创与本土化适配 | 官方不支持国产库，社区方案须 POC；驳回/加签须自研扩展层 | 普遍原生支持国产库与本土化审批 | 同 Flowable，且无后续演进 | 国产库适配与嵌入式集成均不适用 [^2^] |
| 成本结构 | 零许可费，须预算 SDK 扩展、国产库适配、开源治理投入 | 许可与实施费高昂，且伴随厂商锁定 | 存量路径，新建不建议 | 企业许可 + 分布式基础设施成本 |

对比表揭示关键收敛：Camunda 7 社区版终止后，"嵌入式 Java 引擎 + 关系库"这一最契合银行技术栈的开源路线仅剩 Flowable 一个活跃选项 [^5^][^6^]；Camunda 8 的最终一致模型与纯远程部署形态同审批链强一致诉求、行内嵌入式集成习惯均不匹配 [^3^][^2^]。选型由此收敛为"开源 + 自研扩展"与"商业采购"的二元权衡：前者以工程投入换技术自主，后者以采购成本换开箱即用，无脱离机构禀赋的普适最优解。

### 1.2.2 行业采用格局

国内银行流程平台建设的公开案例呈现清晰的机构分层格局：

表 1-3 国内银行流程平台建设案例格局

| 机构类型 | 代表案例 | 技术路线 | 关键事实 |
|---|---|---|---|
| 农信/省联社 | 福建省农村信用社联合社 | 采购商业 BPM | 2023 年公开招标流程引擎系统（限价 150 万元），炎黄盈动 80 万元中标 [^8^] |
| 农信/省联社 | 江西省农村信用社联合社 | 采购商业 BPM | 2023 年度项目 218 万元成交，覆盖集中作业、信贷、统一授信三类引擎 [^9^] |
| 城商行 | 杭州银行 | 开源 Activiti → 外购中台 | 原"自研+Activiti 并行"，后外购微宏 AlphaFlow 统一替换，承载 10+ 系统 [^10^] |
| 股份制银行 | 广发银行深圳分行 | 开源引擎自研 | 公开招聘 Flowable/Activiti 二次开发岗位，佐证内部开源自研体系 [^11^] |
| 股份制银行 | 民生银行 | 企业级统一流程中心 | 官方披露接入 1300+ 业务流程、2000+ 待办、1800+ 消息场景 [^12^] |

格局表支撑三点判断。其一，中小行以采购为主流，原因在禀赋而非技术：商业产品自带国产库适配与本土化审批操作，恰好命中其团队有限、信创压力刚性的约束组合。其二，杭州银行"开源→外购"演进说明开源路线存在隐性成本临界点——接入规模上量后，自建扩展层维护成本可能反超采购成本。其三，广发与民生案例证明基于开源引擎建设全行级流程平台是行业可验证路径，前提是持续投入与平台化治理。

### 1.2.3 决策框架与本设计的前提假设

选型按四维框架执行：**团队规模**（能否持续投入扩展层建设）、**信创要求**（目标库若为国产库，此为开源路线最大技术风险，必须前置 POC 而非假设可行）、**流程复杂度**（接入规模是否超过自建扩展层的经济临界点）、**长期演进**（是否要求规避厂商锁定）。结论随禀赋而异：中小行通常收敛至采购，大中型银行可选开源路线。

本设计文档基于如下前提展开：**目标机构选择 Flowable 开源路线**，拥有可沉淀"流程操作 SDK"与合规归档层的平台团队；目标数据库若为国产库，按第 9 章路线图第一阶段完成适配 POC 后再全面开发。

## 1.3 版本基线与关键约束

### 1.3.1 引擎版本基线

本设计以 **Flowable 8.0.0 / 7.x 线**为版本基线。8.0.0 于 2026 年 2 月发布，基线升级至 Spring Framework 7 / Spring Boot 4 / Jackson 3，不再支持 Spring Boot 3 [^4^][^13^]；7.x 线（7.0.0 于 2023-09-21 发布）对应 Spring Boot 3 / Jakarta EE 9+ / Java 17+ [^14^][^15^]，7.2.0 于 2025-08-21 发布 [^16^]；6.x 止于 6.8.1（2024-02-22，Spring Boot 2.7 基线），官方已不再更新 [^17^]。

版本选择与行内技术栈联动：Spring Boot 3 平台采用 7.x 线；新建平台直接对齐 8.0.0 + Spring Boot 4 + Java 17+，两条线引擎内核与 BPMN/DMN 语义一脉相承，本文结论均适用。需提示：8.0.0 已披露高危 XXE 漏洞（CVE-2026-91197），生产部署应跟踪补丁版本并保持 `flowable.process.enable-safe-xml=true` [^18^]。

### 1.3.2 关键版本事实与迁移约束

从 6.x 迁移至 7.x/8.x 时，三个版本事实直接影响架构设计：

1. **引擎边界收敛**：7.0.0 起聚焦 BPMN/CMMN/DMN/事件注册四大引擎与 REST API，移除全部 UI 应用、Form 引擎与 Content 引擎 [^14^][^19^]——流程设计器、待办界面、表单渲染均须自建，引擎只提供后端能力。
2. **IDM 引擎保留**：被移除的是 IDM **UI 应用**，IDM 引擎仍随主线发布 [^19^]。但行内用户/组权威数据在统一认证系统，本设计不以引擎 IDM 表为身份主数据，仅作候选人解析的可选映射层（详见 8.3.1 节）。
3. **异步历史配置已移除**：6.x 时代的 `asyncHistoryEnabled` 自 7.0 起不复存在，历史数据在引擎事务内同步写入。这消除了"异步历史丢失"的旧隐患，但历史级别（audit/full）对主事务性能的影响也更直接——历史与归档策略因此成为第 8 章非功能设计的独立议题。

### 2.1 客户尽职调查（KYC/CDD）要求

#### 2.1.1 现行规章与新旧切换

客户尽职调查（Customer Due Diligence, CDD）的现行部门规章为〔2025〕第 11 号令，2025 年 10 月 31 日公布、2026 年 1 月 1 日施行[^21^]。两个高频错误须排除：2022 年 1 号令暂缓施行后**从未生效**[^33^]；2007 年 2 号令已被第 52 条明文废止[^21^]。第 7 条将尽调措施分为身份核实、目的了解、资金来源了解、持续尽调、受益所有人识别五项[^21^]，条款级参数必然随细则调整，构成规则外置的刚性需求。

#### 2.1.2 身份识别要素清单：资料清单模板的设计输入

11 号令第 49 条规定身份基本信息法定清单：自然人客户为俗称"九要素"（姓名、性别、国籍、职业、住所地或工作单位地址、联系方式，证件种类、号码、有效期限）；对公客户要素含名称、住所、经营范围、执照证件名称/号码/有效期限及法定代表人、授权经办人身份信息[^21^]。第 9 条要求建立业务关系（含开立账户）及人民币 5 万元以上、外币等值 1 万美元以上一次性金融服务时开展尽调并留存证件影印件[^21^]；第 22 条将联网核查公民身份信息系统列为法定核实渠道[^21^]，对公侧另有企业信息联网核查系统提供登记、纳税、手机号码核验[^35^]。据此，资料清单模板按客户类型参数化、由合规岗维护；核查类义务可自动化为并行 ServiceTask（见 6.2 节）。

#### 2.1.3 新《反洗钱法》与 10 年留存

新修订《反洗钱法》2025 年 1 月 1 日施行[^36^][^20^]："客户身份识别"升级为"客户尽职调查"并包含受益所有人核实（第 28、29 条）[^20^]；存续期持续尽调入法，高风险情形可限制交易乃至终止业务关系（第 30 条）[^20^]；资料保存年限由至少 5 年延长至**至少 10 年**（第 34 条）[^1^][^37^]，11 号令第 44 条同口径[^21^]。10 年留存与 Flowable 历史清理默认窗口（365 天）结构性错配，须自建合规归档层（见 5.3 节）。

### 2.2 受益所有人识别与备案

#### 2.2.1 〔2024〕第 3 号令：备案制度与 25% 穿透标准

《受益所有人信息管理办法》（〔2024〕第 3 号令，2024 年 11 月 1 日施行）确立备案制度[^22^]：备案主体为公司、合伙企业、外国公司分支机构等，个体工商户无需备案；注册资本不超过 1000 万元且股东全部为自然人、无外部自然人控制或获益的，承诺后免报[^22^]。识别标准为"25% 以上"三标准：直接或间接最终拥有 25% 以上股权权益、最终享有 25% 以上收益权或表决权、单独或联合实施实际控制，均不满足的以日常经营管理人员兜底[^22^]。设计要点：标准含本数，备案指南明确持股恰好 25% 者应予备案[^38^]，阈值参数化不得写成"超过 25%"；识别须层层穿透至自然人，间接持股按各层比例连乘[^39^][^38^]。备案信息 8 项要素加 3 类补充字段[^22^]，即 UBO 数据字典的字段基线。

#### 2.2.2 〔2025〕第 12 号令：核对义务、差异报告与存量时间表

《金融机构客户受益所有人识别管理办法》（〔2025〕第 12 号，2026 年 1 月 20 日施行）将银行侧义务具体化，同时废止银发〔2017〕235 号与〔2018〕164 号[^23^]。一是核对义务：对符合备案范围的客户，应将识别结果与人民银行受益所有人信息查询管理系统核对（第 23 条）[^40^]。二是人机边界：第 4 条禁止仅以系统查询或批量化、自动化手段代替必要的风险判断[^40^]，是"监管判断动作必须人工节点"原则的明文依据。三是差异处置：重大差异自发现之日起 **30 个工作日内**提交差异报告（第 27 条），应备未备且提示后仍未备案的亦须报送（第 30 条）[^24^]。四是存量时间表：施行起 6 个月内完成较高风险以上存量客户、2 年内完成全部（第 39 条）[^23^]。"未实质开展识别核实"属情节严重情形（新《反洗钱法》第五十三条，情节严重时处 20 万元以上 200 万元以下罚款）[^41^]，设计应默认监管取证场景。

### 2.3 对公账户管理要求

#### 2.3.1 开户许可取消：核准制改备案制与当日报送

人民银行令〔2019〕第 1 号取消企业银行账户许可，企业基本户、临时户由核准制改为备案制[^25^]；配套操作规则为《企业银行结算账户管理办法》（银发〔2019〕41 号附件 1，2019 年 2 月 25 日起执行）[^26^][^27^]。直接相关条款：法定开户证明文件仅营业执照、法定代表人有效身份证件、授权书及被授权人证件 3 类（第 7 条）；开立基本户须在人民币银行结算账户管理系统审核唯一性，并向法定代表人核实开户意愿、留存记录（第 9 条）；开户信息"立即至迟于当日"向人民银行备案，2 个工作日内报送开户资料（第 13 条）；账户自开立之日即可收付款（第 15 条）[^27^]。2003 年 5 号令"开户 3 个工作日后方可付款"对企业账户已停止执行，账户状态机不得沿用。

#### 2.3.2 账户风控：反电诈法、断卡惩戒与小微简易开户

《反电信网络诈骗法》（2022 年 12 月 1 日施行）将账户风控升至法律层级：第 15 条要求建立尽调制度、依法识别受益所有人；第 16 条规定开户不得超出国家限制的数量，异常开户有权加强核查或拒绝[^28^]。"断卡"行动确立对出租、出借、出售、购买账户者"5 年内暂停银行账户非柜面业务并不得新开账户"的惩戒[^42^][^43^]，受理环节须前置校验惩戒名单。银发〔2021〕260 号确立小微简易开户"先开户、限功能、后升级"模式，账户功能与风险等级相匹配，并要求对拒绝开户建立复核、向客户说明理由[^30^][^31^]。时限上，核准制"2+2"口径（银行 2 个工作日 + 人民银行 2 个工作日，银发〔2017〕288 号）[^44^]在核准制取消后不再作为强制时限适用，现行要求为依《优化营商环境条例》第 26 条公示办理时限并接受监测[^32^]；开户 SLA 基准因此是"本行公示时限"，计时器阈值应配置化。

### 2.4 名单筛查与风险评级

#### 2.4.1 五类名单库、交易前实时筛查与当日上报

银反洗发〔2018〕19 号第 48 条要求建立并及时更新反洗钱监控名单库，涵盖五类：有权部门发布的涉恐名单、联合国发布且我国承认的制裁决议名单、我国承认的其他国际或境外名单、人民银行要求关注的名单、内部关注名单[^29^]。第 49 条规定涉及资金交易的应在**交易完成前**实时监测，名单调整时对存量客户及上溯三年内交易回溯调查，实行精准匹配自动识别或"模糊匹配系统初筛 + 人工分析最终识别"[^29^]；第 50 条要求命中后立即采取措施（含停止账户开立）并**于当日**报告人民银行[^29^]。据此：名单筛查是开户决策前的阻塞式节点；模糊命中须落人工甄别 UserTask；名单更新须触发存量回溯异步批处理。

#### 2.4.2 风险评级与强化尽调依据的切换

风险等级分类的原依据银发〔2013〕2 号已于 2026 年 2 月 7 日被人民银行公告〔2026〕第 3 号废止[^34^]，其五级分类法、10 个工作日初评等技术指标仅作方法论参考[^45^]。现行依据为 11 号令：第 25 条要求建立业务关系时及时评估风险、划分等级，最高风险客户至少每年审核 1 次；第 27 条规定强化尽调（EDD）触发条件；第 28 条枚举 EDD 措施，第五项为建立、维持业务关系"需要获得高级管理层的批准"[^21^]。硬约束有二：评级模型与 EDD 触发条件须以 DMN 决策表外置并版本化；高风险客户审批路由须能上收至高级管理层节点，路由规则同样外置。

### 2.5 监管要求到系统设计的映射

前述义务须逐项转译为四类设计约束：**流程节点**、**数据字段/实体**、**审计留痕**（监管取证的最小留痕集）、**留存策略**（统一对齐 10 年）。流程节点的划分遵循人机边界三原则：其一，涉及监管判断与责任的监管动作必须人工节点（UserTask）并留痕；其二，核验类动作全部系统化，落自动化 ServiceTask；其三，系统侧动作全部幂等，重复触发不产生副作用。三原则的架构落地见 3.1.2 节。映射结果见表 2-2。

## 3. 总体架构设计

第 2 章已将监管义务转译为节点、数据、留痕与留存四类约束，本章回答这些约束落在何种架构骨架上，围绕四个决策展开：流程服务形态（3.1）、五层划分（3.2）、数据分离（3.3）、高可用与信创适配（3.4、3.5）。

### 3.1 架构模式决策

#### 3.1.1 独立流程服务而非嵌入式

Flowable 支持嵌入式（引擎作为类库与业务系统同进程）与独立服务两种形态。嵌入式的主要收益是事务一致性：业务与引擎共用 DataSource 和同一事务管理器，即可实现"引擎失败业务回滚、业务失败引擎回滚"的本地事务，无需 XA/JTA[^46^][^47^]；独立部署失去这一便利，跨服务一致性须以 Transactional Outbox 模式加消费端幂等兜底[^48^]。

本设计选择**独立流程服务（流程平台）形态**，理由有三。其一，多渠道复用：柜面、客户经理 APP、网银预约共用准入逻辑，引擎嵌入任一渠道都会使其余渠道反向依赖它，独立部署使流程成为渠道无关的共享能力。其二，统一待办：民生银行官方披露其流程中心接入 1300+ 个业务流程、统一待办中心接入 2000+ 种待办任务[^12^]，杭州银行中台以 API/SDK"纯后端接入"[^10^]——准入待办须汇入全行统一待办体系，独立流程服务是其自然提供者。其三，独立演进：流程骨架、DMN 规则与引擎版本须独立于渠道发版。

代价须明示：独立部署放弃本地事务，申请单与流程实例的状态一致性改由"业务库 Outbox + MQ + 幂等消费"保证（3.2.2、3.3.1）。

#### 3.1.2 人机边界三原则

UserTask 与 ServiceTask 的划分以监管责任为界，遵循第 2 章确立的三原则。**监管动作人审**：涉及判断与责任的节点必须是 UserTask 并留痕——〔2025〕第 12 号令第 4 条禁止仅以批量化、自动化手段代替必要的风险判断[^40^]，名单筛查须"模糊匹配系统初筛 + 人工分析最终识别"（银反洗发〔2018〕19 号第 49 条）[^29^]；模糊命中甄别、UBO 识别、EDD 高管批准、拒件复核均落人工节点。**核验动作系统化**：联网核查、名单初筛、备案核对无自由裁量成分，建模为异步 ServiceTask（`flowable:async="true"`）并行编排。**系统动作全部幂等**：ServiceTask 会被重试、被他节点重复抢占，下游调用（核心开户、人行备案报送）须携带全局唯一幂等键并在服务端防重[^49^][^50^]；重试耗尽进死信表后不再自动执行，须配死信监控与人工重放通道[^51^]。

### 3.2 分层架构

#### 3.2.1 五层结构与职责划分

系统自顶向下划分为渠道、接入、流程、业务、集成五层。一次准入申请的分层流转如下（编号即请求路径）：

1. 渠道层采集申请要素与影像，调接入层准入 API 提交；
2. 接入层完成鉴权、参数校验与幂等判重，生成申请编号 applyNo，落业务层申请单；
3. 接入层以 applyNo 为 businessKey 调流程层启动流程实例；
4. 流程层按 BPMN 骨架推进：调 DMN 输出资料清单与风险评级，路由结果回写业务层，人工任务经事件通知接入层聚合待办；
5. 业务层承载全部业务状态与表单数据，流程层不持有业务正文；
6. 流程层系统任务经集成层 Adapter 群调用行内外服务（联网核查、名单筛查、核心开户、备案报送等），结论写业务层，变量只保留结论与引用 ID；
7. 核验结论与审批意见全程写入业务层审计流水，满足 10 年留存（详见 5.3 节）。

表 3-1 分层职责表

| 层 | 核心构件 | 职责 | 禁止事项 |
|---|---|---|---|
| 渠道层 | 柜面、客户经理 APP、网银预约 | 要素采集、影像上传、进度查询 | 不含审批规则与状态机 |
| 接入层 | 准入 API 门面 | 鉴权、幂等判重、编号签发、待办聚合 | 不直接操作引擎表 |
| 流程层 | BPMN 引擎、子流程、DMN、操作 SDK | 流程推进、规则求值、审批操作语义化 | 不存业务正文，变量只放轻量标量 |
| 业务层 | 申请单、草稿、清单、审计流水、待办宽表 | 业务状态权威源、留痕、查询模型 | 不感知流程执行结构 |
| 集成层 | Adapter 群（核查/名单/核心/备案/影像） | 协议适配、幂等键管理、报文留档 | 不含分支判断，结论原样回传 |

职责表含两条设计红线。其一，"流程层不存业务正文"：Flowable 读取任一变量时默认抓取该执行的全部变量，audit 级别变量持续同步历史表，大变量成倍放大写入[^52^][^53^]，故资料正文、影像、报文一律落业务层。其二，"集成层不含分支判断"：Adapter 只负责调用与报文留档，结论路由由流程层表达，Adapter 可独立替换——联网核查接入形态（经人民银行信息转接系统的接口方式、直连兜底）变更时不动流程图[^54^]。操作 SDK 列入流程层，是因驳回/加签等引擎能力碎片化且各有边界问题，须统一封装后暴露语义接口（4.4 节展开，代码骨架见第 7 章）。

#### 3.2.2 编排与协同分工

流程层内部按"审批段编排、系统段协同"分工。**审批段**（尽调→评级→审批→开户）状态迁移强有序、责任链清晰，用 BPMN 顺序流与网关显式编排，DMN 以 `type="dmn"` 决策任务嵌入求值（Flowable DMN 表达式语言为 JUEL，不支持 FEEL）。**系统段**（并行核验、备案报送、影像归档、进度通知）与主流程是"触发—反馈"关系，用 MQ 事件协同：任务经 Outbox 发事件，Adapter 消费执行并回写结果，结果事件驱动流程继续。理由有二：性能上避免流程图内高频轮询外部状态——官方论坛实例表明"每分钟定时轮询外部服务"会使 act_hi_actinst 爆炸式增长[^55^]；可读性上避免全部系统交互堆进一张 BPMN 形成巨型蜘蛛网图。失败处置亦正交：接口超时走重试与死信，业务拒绝建模为 BPMN Error 走拒绝分支。

### 3.3 数据架构

#### 3.3.1 流程数据与业务数据分离、applyNo 双向关联

引擎自有表（act_*）与业务表（t_*）分 Schema 管理：act_* 由引擎独占读写，t_* 为业务状态权威源。双向关联以申请编号 applyNo 实现：启动流程时以 applyNo 为 businessKey——官方 Javadoc 明确"提供 businessKey 是最佳实践"，运行时与历史表的 BUSINESS_KEY_ 列均有索引，查询性能优于按变量查询[^56^]；反向由业务表记录 processInstanceId。须正视的引擎事实是：**businessKey 唯一约束已于 ACT-1860（2013 年）移除，引擎不保证唯一**[^57^]。幂等防重须自建：在 (PROC_DEF_ID_, BUSINESS_KEY_) 上建唯一索引兜底，接入层先查重再启动，重复提交返回原申请单[^57^]。

#### 3.3.2 CQRS 待办宽表

待办/已办列表是最高频查询，实时 join 引擎运行时表与历史表既慢又拖垮引擎主库，故采用 CQRS 变体：写侧由全局事件监听器（TASK_CREATED/TASK_COMPLETED 等[^58^]）在事务提交后将任务快照写入业务层**待办宽表**（冗余申请人、客户类型、当前节点、受理机构、SLA 剩余等展示字段）；读侧列表只命中宽表，不 join 历史表，详情按需回查。配套约束两条：监听器 `isFailOnException()` 必须返回 false，否则宽表异常回滚引擎事务；监听器只对本引擎实例生效，集群各节点均须注册[^59^]。已办结查询直接读引擎历史表系官方建议[^53^]。

### 3.4 部署与高可用

#### 3.4.1 流程服务集群与 Async Executor

Flowable 集群无协调中间件：多节点共享同一数据库即自动构成集群，作业落库后由任一在线节点抢占执行。防重靠行级锁加租约——作业行写入 lock owner 与锁到期时间，节点崩溃后由过期作业重置线程释放锁供他节点接管。6.7.0 起 Global Acquire Lock 保证同一时刻仅一个节点执行抢占查询，作业可批量获取（官方推荐单次 512 个），大幅降低作业表并发争用[^60^]。据此，流程服务的单点瓶颈在数据库，DB 高可用是集群前提；应用层无状态，前置负载均衡即可水平扩缩。

容量联动有官方明确公式：扩大异步线程池必须同步扩大数据库连接池（每个后台线程需一条连接）；队列容量与锁租约取值须按所选代际联动规划：6.6 及以前默认锁租约 5 分钟；6.7.0 引入全局抢占锁后官方推荐锁租约 1 小时（lock-time=3600000ms），配套队列容量 2048、线程池 32/32[^61^][^60^]。队列过大导致作业滞留超过锁租约、被他节点重复抢占，而多数作业处理器不具幂等性。核验类 Adapter 内置幂等键（3.1.2）即对此的兜底。

#### 3.4.2 关键配置基线

生产基线四项，均有事实依据。其一，`asyncExecutorActivate` **默认 false**，不开启则全部定时器（催办、SLA 超时）不触发，集群至少一个节点须显式置 true[^62^]。其二，`flowable.history-level=audit`：audit 级已覆盖"谁、何时、对哪个任务做了什么、提交了什么表单"的审计语义，full 级最慢，代价与收益不成比例[^53^]。其三，生产关闭 `database-schema-update` 自动建表，改由 DBA 审核的版本化脚本执行——国产库场景下此为硬性要求（3.5）[^63^]。其四，保持 `flowable.process.enable-safe-xml=true`。另需说明：`asyncHistoryEnabled` 自 7.0 起已移除，"开启异步历史提吞吐"的旧经验在 7.x/8.x 基线下不适用。

### 3.5 数据库与信创适配策略

#### 3.5.1 官方支持边界与国产库适配坑点

Flowable 开源版 databaseType 官方仅支持 {h2, mysql, oracle, postgres, mssql, db2} 六种[^59^]；企业版测试矩阵同样不含任何国产库，官方口径为"JDBC 可连但不官方支持、未经测试"[^64^]。国产库适配因此全部是**社区补丁路线**：将 databaseProductName 映射到已有方言复用其脚本，或新增类型加差异脚本；虽有产品化参照（yudao 的达梦补丁含 DmDatabase、BooleanType 覆盖类与 SPI 注册[^65^]），均属社区方案，须 POC 验证。各库已知坑点如下。

表 3-2 国产数据库适配坑点表（社区方案，均须 POC 验证）

| 数据库 | 接入路线 | 已知坑点 | 缓解措施 |
|---|---|---|---|
| 达梦 DM | Oracle 兼容模式复用 oracle 方言 | Liquibase 的 CURRENT_SCHEMA、BooleanType 转换报错[^66^][^63^] | 关自动建表、版本化脚本；引入补丁包[^65^] |

## 4. 流程建模设计

本章将第 2 章的监管映射表（表 2-2）转译为可执行的 BPMN/DMN 模型，遵循三条前提：其一，监管依据密集换版，随细则调整的规则一律外置为 DMN 决策表，BPMN 图只表达稳定骨架；其二，人机边界以监管责任为界——涉及判断与责任的节点（UBO 识别、模糊命中甄别、EDD 高管审批、拒件复核）必须是 UserTask 并留痕，核验类义务落异步 ServiceTask；其三，驳回、加签、会签等"中国式审批"操作不直接暴露引擎原生 API，由平台操作 SDK 封装（4.4 节，代码骨架见第 7 章）。版本基线为 Flowable 8.0.0（2026 年 2 月发布）[^77^]，跨版本一致的 API 会注明引入版本。

### 4.1 流程分层与拆分策略

#### 4.1.1 按客户类型分定义，共用部分抽 Call Activity 子流程

对公与个人准入在三个维度上结构性不同：身份要素清单不同（11 号令第 49 条分自然人"九要素"与法人要素两套）[^21^]；核验通道不同（个人走人民银行会同公安部建成的联网核查公民身份信息系统[^78^]，对公另走企业信息联网核查系统）[^35^]；审批链路不同（对公存在受益所有人穿透与 EDD 上收）。故按客户类型拆两个主流程定义，跨类型复用的监管动作抽为 Call Activity 子流程，见表 4-1。

表 4-1 流程定义拆分表

| 流程定义 key | 类型 | 适用对象/触发条件 | 涵盖节点段 | 拆分理由 |
|---|---|---|---|---|
| onboarding-corp | 主流程 | 企业、非法人企业、个体工商户 | 受理尽调→并行核验→评级审批→开户归档 | 对公要素、UBO 穿透、意愿核实独有 |
| onboarding-retail | 主流程 | 自然人客户 | 受理尽调→并行核验→评级审批→开户 | 九要素、I/II/III 类户规则不同 |
| sub-edd | Call Activity 子流程 | 高风险、或命中 11 号令第 27 条情形 | 强化尽调执行→高级管理层批准 | 独立监管动作，对公/零售复用 |
| sub-supplement | Call Activity 子流程 | 任一审核节点判定资料不全 | 补件通知→补件接收→要素重新校验 | 高频循环路径，独立建模避免主图回环 |

拆分的收益是变更隔离：对公侧受益所有人规则调整只影响 onboarding-corp 及其引用的 DMN，零售链路零回归；sub-edd 可单独版本化，措施清单调整不触动主流程。代价是跨定义观测须以 businessKey（准入申请编号）串联；引擎不保证 businessKey 唯一，幂等须在业务表自建唯一索引（见 5.1 节）。

#### 4.1.2 拒绝巨型图：一张图一类客户，网关分叉不超过三层

"巨型图"在引擎层面没有硬性限制，但工程代价确定：实例迁移需逐活动映射，图越大迁移越脆弱（4.5 节）；网关嵌套过深导致条件组合爆炸、测试无法穷举；规则硬编码进网关则每次监管调整都要改图发版。由此确立两条纪律：一张主流程图只服务一类客户；排他网关分叉不超过三层，更深分流下沉到 DMN 审批路由表。规则外置后，流程图变更频率可降至年度级（Insight 1）。

### 4.2 对公准入主流程（节点级设计）

onboarding-corp 节点骨架如下，每节点标注类型 | 角色/系统 | SLA 与定时器。SLA 基准是本行依《优化营商环境条例》第 26 条公示的开户办理时限[^32^]，取值全部配置化，不写入流程定义。

#### 4.2.1 受理与尽调段（节点 1—4）

1. **申请受理与要素校验**（ServiceTask，异步 | 系统 | 秒级）：按 11 号令第 49 条对公要素清单校验完整性[^21^]；前置校验"断卡"惩戒名单（5 年内不得新开账户）[^42^]与开户数量限制（反电诈法第 16 条）[^28^]。
2. **客户经理尽调**（UserTask | 客户经理 | SLA=P3D，非中断定时器催办）：录入尽调五项措施结论（11 号令第 7 条）[^21^]；资料不全不驳回，转入补件子流程。
3. **补件子流程**（Call Activity，sub-supplement | 客户经理/客户 | SLA=P5D）：补件后回步骤 2 复核，构成"尽调⇄补件"循环而不污染主图。
4. **开户意愿核实**（UserTask | 柜面/视频坐席 | SLA=P1D）：基本户须向法定代表人核实意愿并留痕，面签或视频按风险选择（《企业银行结算账户管理办法》（银发〔2019〕41 号印发，下称"41 号办法"）第 9 条）[^27^]。

#### 4.2.2 并行核验段（节点 5—9）

5. **并行核验段 fork**（并行网关）：三条并行分支（以异步 ServiceTask 为主，名单筛查与受益所有人分支内嵌人工甄别/确认 UserTask），结论齐备后 join 汇聚。
6. **名单筛查**（ServiceTask，阻塞式 | 名单筛查系统）：对五类名单库精准匹配+模糊初筛（银反洗发〔2018〕19 号第 48—49 条）[^29^]；模糊命中产生 **模糊命中甄别**（UserTask | 合规岗 | SLA=PT4H），确认命中须**当日**上报并可停止开户（第 50 条）[^29^]——全流程唯一"当日"级硬约束，挂中断型超时升级定时器。
7. **联网核查+企业信息联网核查**（ServiceTask，异步 | 人民银行核查通道）：法定代表人及经办人经联网核查公民身份信息系统核实（11 号令第 22 条）[^21^]，企业登记、纳税、手机号码经企业信息联网核查系统核验[^35^]；配 `flowable:failedJobRetryTimeCycle="R3/PT10M"` 退避重试，耗尽进死信转人工[^61^]。
8. **受益所有人穿透与核对**：穿透计算（ServiceTask | 系统）按 25% 三标准连乘算候选自然人[^22^]；**UBO 识别确认**（UserTask | 客户经理+合规复核）人工判断——12 号令第 4 条禁止以系统查询或批量化手段代替必要的风险判断[^40^]，不可自动化闭环；备案核对（ServiceTask）对接人民银行受益所有人信息查询管理系统（12 号令第 23 条）[^40^]；重大差异触发差异处置分支（12 号令第 27 条，发现差异之日起 30 个工作日内提交差异报告，timeDuration 定时器）[^24^]。
9. **并行核验段 join**：任一路失败或确认命中，进**异常处置**（UserTask | 合规岗）：终止流程（拒件复核，须向客户说明理由，银发〔2021〕260 号）[^31^]或退回步骤 2。

#### 4.2.3 评级与审批段（节点 10—13）

10. **DMN 风险评级**（ServiceTask，flowable:type="dmn" | 规则引擎）：调用 dmn-risk-rating，输出 riskLevel 与 decisionRoute 写回流程变量（4.3.1 节）。
11. **风险分流网关**（排他网关，只读 decisionRoute 变量）：HIGH→sub-edd；MEDIUM→分行审批；LOW→网点审批；阈值不写在网关上。
12. **EDD 子流程+高管批准**（Call Activity，sub-edd | 客户经理/高级管理层 | SLA=P10D）：执行 11 号令第 28 条措施，第五项"需获得高级管理层的批准"落为总行高管会签 UserTask（多实例并行）[^21^]。
13. **分行/网点审批**（UserTask | 分行风险部/网点负责人 | SLA=P2D/P1D）：低风险网点终审，中风险分行终审。

#### 4.2.4 开户与归档段（节点 14—17）

14. **核心开户**（ServiceTask，异步 | 核心系统）：幂等键=申请编号+账户类型，唯一索引兜底；挂补偿边界事件，后续失败触发账户冲正。
15. **开户备案报送**（ServiceTask，异步 | 账户管理系统）：开户信息"立即至迟于当日"备案、2 个工作日内报送资料影像（41 号办法第 13 条）[^27^]，非中断定时器超时预警。
16. **印鉴建档/签约→影像归档**（ServiceTask ×2 | 运营/影像平台）：归档对接 5.3 节三层留存方案，满足 10 年留存（新《反洗钱法》第 34 条）[^1^]。
17. **发布准入完成事件**（ServiceTask | MQ/Outbox）：向账户、额度、渠道系统广播 customer-onboarded 事件。

骨架有三处结构性决策。第一，名单筛查置于开户决策**之前**且阻塞并行段：19 号文要求交易完成前实时监测、命中可停止开户[^29^]，后置为开户后核查则只能事后管控。第二，UBO 识别确认与模糊命中甄别两个人工节点嵌在并行分支内部，不阻塞其他分支的系统核验，仅延长 join 等待——兼顾自动化率与人工甄别要求。第三，开户备案建模为开户**之后**的独立 ServiceTask："当日备案"时限与开户成功解耦，备案通道故障不应回滚已开立账户，由死信队列与超时预警保证当日补齐。

### 4.3 DMN 决策表设计

#### 4.3.1 风险评级决策表：输入维度、JUEL 表达式与 hit policy

dmn-risk-rating 输入取四维度：名单筛查结论、行业风险、地域风险、预期交易规模。Flowable DMN 明确不支持 (S)-FEEL，开源版仅支持决策表一种决策逻辑类型（表达式语言为 JUEL）[^79^][^80^]。hit policy 选 FIRST 而非 UNIQUE：评级规则天然存在维度重叠，UNIQUE 要求规则完全不相交，会迫使重叠组合展开为笛卡尔积行，细则微调时极易漏行；FIRST 按行序取首个命中，最严规则置顶、兜底行置底，与"就高不就低"语义一致。Flowable 共支持 7 种 hit policy[^79^]，本章用法：评级与路由用 FIRST（带兜底行），清单模板用 COLLECT 汇总多维度资料要求。示例见表 4-2。

表 4-2 dmn-risk-rating 决策表设计示例（hitPolicy=FIRST，按行序命中）

| 规则 | screeningResult（名单结论） | industryRisk（行业） | regionRisk（地域） | annualAmount（万元） | 输出 riskLevel | 输出 decisionRoute |
|---|---|---|---|---|---|---|
| R1 | == 'CONFIRMED_HIT' | — | — | — | HIGH | REJECT |
| R2 | == 'CLEARED' | == 'HIGH' | — | — | HIGH | EDD_HQ |
| R3 | == 'CLEARED' | — | == 'HIGH' | — | HIGH | EDD_HQ |
| R4 | == 'CLEARED' | == 'MEDIUM' | — | > 5000 | MEDIUM | BRANCH |
| R5 | == 'CLEARED' | — | — | — | LOW | OUTLET |

表 4-2 的设计意图有三层。其一，R1 置顶体现名单结论的绝对优先：确认命中无论其他维度如何都路由至 REJECT（对应 4.2 节拒件复核），与 19 号文"命中后立即采取措施"一致[^29^]。其二，R2/R3 与 R4 的行序构成"或条件就高"语义：行业或地域任一高风险即上收 EDD，中风险行业须叠加金额阈值才升档——行序即优先级，FIRST 使该语义显式化。其三，R5 为无条件兜底行，决策任务同时配置"无规则命中时报错"作双保险[^81^]，避免兜底行被误删后网关读不到 decisionRoute 变量而悬停。决策输入输出快照由引擎自动落入 ACT_DMN_HI_DECISION_EXECUTION 审计表[^82^]，满足"评级依据可重现"的取证要求；8.0.0 新增的可关闭 DMN 历史持久化选项须保持默认（保留历史），不得为吞吐牺牲审计[^4^]。

#### 4.3.2 审批路由与资料清单模板：细则变更只改表不改图

另设两张决策表。dmn-approval-route（FIRST）以 riskLevel、账户类型、机构归属为输入，输出审批层级与审批人候选组表达式，"高风险上收总行会签"这类阈值调整不动 BPMN。dmn-doc-checklist（COLLECT）以客户类型、账户类型、简易开户标志为输入，汇总输出资料清单——法定基线为营业执照、法定代表人身份证件、授权书及被授权人证件 3 类（41 号办法第 7 条）[^27^]，简易开户按银发〔2021〕260 号不得"一刀切"追加辅助材料[^31^]。三张表由合规岗维护、独立部署；DMN 与 BPMN 同样按 key 递增版本、按 key 执行默认取最新[^80^]，规则热更新无需重启或重新部署流程——这是"只改表不改图"的引擎机制基础。

#### 4.3.3 能力边界：无 FEEL、仅决策表，复杂评分卡留给专用规则引擎

Flowable DMN 的边界须在设计阶段写明。第一，不支持 FEEL，数值区间只能以 JUEL 比较表达式逐格展开[^79^]。第二，开源版仅支持决策表，无嵌套 boxed expression 与业务知识模型（BKM）；DRD/决策服务编排面向企业版，开源 Modeler 支持不完整[^83^]，多表编排（评级→路由）以流程上两个顺序决策任务实现。第三，决策表是无状态的"条件→结论"映射，不具备推理链与模式匹配能力：未来引入统计评分卡、规则链推理或 Rete 匹配时，应集成 Drools 类专用引擎（DMN 实现达 conformance level 3，另有 DRL 支持前向/后向链推理）[^84^]；集成通道已预留——Business Rule Task 可挂自定义 delegate 调用外部规则服务[^85^]，替换不改流程骨架。

表 4-3 揭示一个共性：引擎提供的是运行时状态变更原语而非预设审批服务——目标合法性、并行收拢、子流程历史保护、计票语义全部落在 SDK（Insight 3）。SDK 须内置变量清理、历史快照、并行域识别与计票器四类补偿逻辑，并以集成测试覆盖"驳回×并行×子流程"组合矩阵。三个最易踩坑点展开如下。

**驳回的版本事实须先纠偏**。社区流传"ChangeActivityStateBuilder 自 6.4.0 引入"不准确：接口本体 6.2.0 已存在（仅实验性方法），完整 move* 系列自 **6.3.0** 进入正式版[^86^]；6.6.0 才增 newAssigneeId 重载[^93^]。驳回后目标节点创建全新任务实例，assignee 按定义重新解析；每次 changeState 都重建 execution，executionId 不可用于追踪轨迹[^88^]。从 CallActivity 跳回父流程时子流程历史被物理删除且行为硬编码[^90^]——对监管取证不可接受，SDK 的先快照后迁移是不可省略的补偿。

**会签的计票语义必须自定义**。内置变量 nrOfInstances/nrOfActiveInstances/nrOfCompletedInstances 只统计完成数量[^85^]，`${nrOfCompletedInstances==nrOfInstances}` 表达"全员处理完毕"而非"全员同意"——拒绝也算完成。合规敏感场景下，SDK 在 complete 事件 TaskListener 中累计 approvedCount/rejectedCount，completionCondition 调后端计票方法判断何时结束，通过/拒绝方向由后续排他网关按计票变量路由[^94^]；"一票否决"即 rejectedCount≥1 提前结束。

**催办与超时升级共享边界定时事件但语义相反**。催办用非中断模式（cancelActivity="false"）+ timeCycle（如 R3/PT24H），原任务保持可办；超时升级用默认中断模式收回任务转上级。两个运维事实须写入 SLA 设计：定时器仅在 async executor 激活时触发（默认 false，生产必须显式开启）；触发延迟受 acquire 轮询影响为 10 秒量级，宕机期间到期定时器恢复后补执行——对外 SLA 粒度为分钟级，不承诺秒级[^61^]。

### 4.5 流程版本与灰度

#### 4.5.1 版本化语义：在途不自动切新版，显式迁移有边界

部署规则为：同 key 递增版本号，id 形如 `key:version:generatedId`；按 key 启动默认取最新版本，而**在途实例继续运行于创建时的版本，不自动切换**[^95^][^96^]。需在途切换时，官方正道是 6.4.0 引入的 ProcessInstanceMigrationBuilder（支持 validateMigration 预校验与活动映射）[^97^]；Activiti 5 遗产的 SetProcessDefinitionVersionCmd 仅存于 impl 内部包、未经 RuntimeService 暴露，不得使用[^98^]。迁移有明确边界：等待态同名活动映射、并行网关内外迁移、父子流程迁移均支持，但**不支持多实例执行集合整体迁移、不支持迁入多实例活动**[^97^]——会签中的在途单无法切换，只能走完旧版。

#### 4.5.2 监管新规上线策略：流程与 DMN 双轨，在途走旧版为原则

监管细则切换按"新流程版本+新 DMN 版本"双轨发布：新申请按受理日期路由到新流程定义版本；在途单原则上走旧版至办结。有一个引擎机制带来的例外须显式管控：DMN 按 key 执行默认取**最新**版本[^80^]，在途旧流程到达决策任务时实际执行新表。多数变更新旧并行不悖（新表更严），可接受；新规含"施行日前已受理按旧口径"过渡条款时，须以部署引用锁定 DMN 版本，或以受理日期作为决策表输入维度在行内分流——后者与"规则外置"自洽，为默认选择。切换窗口期由合规岗登记生效日期，形成"监管发文→决策表新版→灰度观察→全量"闭环，流程图在此过程中不变。

## 5. 数据模型设计

本章将第 3 章"流程数据与业务数据分离"原则落到表结构层面，回答四个问题：业务状态存在哪里（5.1）、流程变量允许放什么（5.2）、10 年留存如何实现（5.3）、高频查询如何支撑（5.4）。前提有二：applyNo 即 businessKey，业务表以 process_inst_id 反向关联流程实例；唯一性约束已于 ACT-1860 被引擎移除，幂等须自建唯一索引兜底[^57^]；全部留痕须满足新《反洗钱法》第 34 条"至少保存十年"[^1^]。

### 5.1 业务表设计

#### 5.1.1 业务表清单与设计总则

业务层共 8 张表，按"主档—明细—留痕—查询"四类组织，清单见表 5-1。

#### 5.1.2 t_onboarding_apply 申请主表 DDL 要点

申请主表是全流程的状态枢纽，DDL 要点如下（以 MySQL 8.0 方言示例；国产库方言差异按 3.5 节 POC 结论调整，自动建表一律关闭）。

```sql

  id               BIGINT       NOT NULL AUTO_INCREMENT COMMENT '物理主键',

  risk_level       VARCHAR(8)   NULL COMMENT 'DMN 输出回写：LOW/MEDIUM/HIGH',
```

三个字段级决策须说明。第一，apply_no 唯一索引是幂等地基：接入层"先查重再启动"存在并发窗口，重复提交最终由该索引拒绝，并在 ACT_RU_EXECUTION 的 (PROC_DEF_ID_, BUSINESS_KEY_) 上由实施方**自建**唯一索引作为第二道防线（官方论坛建议做法）[^57^]；注意对引擎表加索引属于非标改动，须纳入引擎版本升级的回归验证清单。第二，status 不暴露业务写接口，只能由流程事件监听器按"实例启动/办结/终止"单向同步，否则业务表与引擎运行时状态分裂。第三，risk_level 与 decision_route 是 DMN 输出的物化：同名流程变量供网关路由（5.2 节），主表冗余一份供列表与复核统计，查询侧无需回查 DMN 历史。

#### 5.1.3 t_customer_draft 草稿隔离与资料、筛查明细表

t_customer_draft 承载尽调过程的客户要素全集（个人九要素、对公要素按 11 号令第 49 条[^21^]），与正式客户主档（ECIF）物理隔离：审批通过前，未核实数据不得刷入主档，否则被拒客户的脏数据将污染全行客户视图；仅在"核心开户"成功后由开户 Adapter 转正并回写客户号。草稿按 (apply_no, version) 留版本、旧版本不删——版本链本身即"客户身份资料"的组成部分，纳入 10 年留存。

t_material_checklist 由 dmn-doc-checklist（4.3.2 节）在受理后初始化，逐行记录资料项、收取状态与 ECM 影像 imageId；影像正文不入库，业务表只存索引，与影像平台按"业务流水号↔影像索引"模式衔接[^99^]，关联失败进人工补录队列[^100^]。t_screening_result 按筛查批次留档：名单库类别（19 号文第 48 条五类名单）、命中类型（精准/模糊）、模糊分值、甄别结论与甄别人全部落表——19 号文要求模糊匹配"再通过人工分析完成最终识别"[^29^]，该表即人工识别的证据载体。

### 5.2 流程变量规范

#### 5.2.1 变量白名单与 4000 字符边界

流程变量只承担"路由与轻量结论"，白名单六项：applyNo、customerType、riskLevel、hitFlag、orgPath、decisionRoute，均为 String/Boolean 标量。引擎依据有二。其一，读取任一变量时引擎默认抓取并缓存该执行的全部变量（get 与 set 均如此），变量越多单次操作的往返越大[^52^]。其二，audit 级别下变量值持续同步至 ACT_HI_VARINST，变量体量直接放大历史写入[^53^]。

String 变量的物理边界是 TEXT_ 列 varchar(4000)：超限自动转 longString 类型，经 BYTEARRAY_ID_ 外键转存 ACT_GE_BYTEARRAY[^101^]。代价不只是多一次表关联——核心开发者对 longString 的设计说明指出其初衷是"变量值并非总被需要，从性能角度不应总是把字节从库传到应用"[^102^]，即每次读取都涉及大字段传输决策；且 ACT_GE_BYTEARRAY 同时存放部署资源，业务大对象混入后该表成为容量热点。据此规定：单变量不得超过 2000 字符（对齐 Oracle 2000 字符边界），资料正文、核查报文、尽调长文本一律落业务表，变量只放引用 ID。

#### 5.2.2 大对象禁令与 transient 变量

两类变量禁用。其一，serializable 对象：无法被查询索引，类版本演进后存量实例反序列化失败。其二，集合型变量承载明细数据：明细是 t_* 明细表的职责。若需在单一事务链内（如同一 ServiceTask 调用链中组装 DMN 输入）传递大对象，使用 transient 变量——引擎对其完全不持久化、不留任何历史[^52^]，事务结束即消失。代价是不可跨等待状态使用，越过 UserTask 或异步边界即丢失，建模时须显式标注其作用范围。

### 5.3 审计与合规留存

#### 5.3.1 三层留存与 365 天清理窗口的冲突化解

引擎能力与监管要求存在结构性错配（Insight 2）：新《反洗钱法》第 34 条要求客户身份资料至少保存十年[^1^]，11 号令第 44 条同样规定 10 年[^21^]；而 Flowable 6.5.0 引入的 History Cleaning 默认删除 365 天前已结束的历史实例及关联数据[^53^]。直接采用默认配置，流程轨迹将在监管期限过半前被物理清除。化解方案为三层留存：

1. **引擎历史层（热层）**：history-level=audit，已覆盖"谁、何时、对哪个任务做了什么、提交了什么表单"的审计语义[^53^]；History Cleaning 不简单关闭（避免历史表无限膨胀），而是与归档批次联动——归档回执确认成功后才清理对应区间。
2. **自定义审计层（温层）**：t_audit_trail 审计流水，由全局事件监听器在事务提交后写入，承载审批意见、驳回快照等引擎历史不覆盖的内容（5.3.2 节）；与业务表同库，随业务备份保存十年以上。
3. **归档层（冷层）**：办结满约定期限的申请，其业务记录、审计流水与影像索引打包归档至 ECM/电子档案系统；归档须满足《会计档案管理办法》（财政部 国家档案局令第 79 号）第八条"仅以电子形式保存"的条件——来源真实、可准确完整读取、防篡改、备份制度等[^103^]；外部电子凭证按财会〔2020〕6 号保留电子原件而非打印件影像[^104^]。

三层以归档批次号衔接：热层清理以"该批次温层与冷层均已确认"为前置条件，保证任意时点任一申请的全套轨迹至少完整存在于一层，监管期限内无留存真空期。

### 5.4 查询与报表

#### 5.4.1 v_todo_worklist 待办宽表

待办列表是全行统一待办体系的输入，也是最高频查询。v_todo_worklist（物理实现为表，对消费方暴露视图）由 3.3.2 节的 CQRS 机制同步：全局事件监听器在 TASK_CREATED、TASK_COMPLETED、TASK_ASSIGNED 事件事务提交后刷新对应行[^58^][^59^]。字段分四组：任务标识组（task_id、process_inst_id、apply_no、activity_id）；展示组（customer_name、customer_type、当前节点名称、申请摘要）；路由组（assignee、candidate_group、org_path——机构级数据权限直接过滤本列）；时效组（task_created_time、sla_deadline，剩余时长查询时计算）。

消费约束两条。其一，宽表只服务列表页；详情页回查业务表，已办结查询直接读引擎历史表——这是官方为降低运行时表压力给出的建议[^53^]。其二，宽表允许重建：以 apply_no 关联重放引擎运行时与历史任务数据即可全量恢复，故不配置与主档同级的容灾等级。报表取数分两类：运营指标（SLA 达成率、驳回率、节点平均耗时）从宽表快照与 t_audit_trail 聚合，不扫引擎历史大表；监管报送（筛查留档核查、尽调完整性抽查）以 t_screening_result、t_verify_record 两张 append-only 表为权威源，报送口径与留存口径天然一致。

## 6. 接口与集成设计

第 3 章已确立两条边界：渠道不直连引擎，外部系统不直连流程。本章落地其具体形态——6.1 节定义对渠道暴露的准入 API 门面及横切要求；6.2 节给出全部外部系统的集成通道与合规要点；6.3 节统一规定横贯两类接口的可靠性模式（幂等、重试死信、补偿）。Adapter 与操作 SDK 的代码骨架见第 7 章。

### 6.1 对外 API 门面

#### 6.1.1 门面接口清单：渠道零感知 Flowable

门面部署于接入层，对柜面、客户经理 APP、网银预约提供统一操作语义，设计约束为"渠道零感知 Flowable"：端点、入参、错误码中不出现任何引擎概念（不暴露 processInstanceId、executionId、activityId），驳回、委派等引擎能力差异由 SDK 封装吸收（见 4.4 节）。接口清单见表 6-1。

表 6-1 准入 API 门面接口清单

| 接口 | 端点（REST 风格） | 引擎/SDK 映射 | 幂等键 | 设计要点 |
|---|---|---|---|---|
| submit 提交申请 | POST /onboarding/applications | RuntimeService.startProcessInstanceByKey(key, applyNo, vars) | 客户端幂等头 + applyNo 唯一索引兜底 | 以 applyNo 为 businessKey 启动；渠道不感知流程定义版本 |
| approve 审批通过 | POST /onboarding/tasks/{taskId}/approve | TaskService.complete(taskId, vars) | taskId + 操作人 + 意见摘要哈希 | 服务端校验认领状态与审批权限 |
| reject 驳回 | POST /onboarding/tasks/{taskId}/reject | 操作 SDK 驳回封装（ChangeActivityStateBuilder 系列，6.3.0+） | taskId + 目标节点 | 目标可达性校验、并行域收拢、历史先快照均在 SDK 内完成 |
| supplement 补件 | POST /onboarding/applications/{applyNo}/supplements | 触发 sub-supplement 子流程/补件完成信号 | applyNo + 补件批次号 | 补件后自动回到尽调复核节点 |
| delegate 委派 | POST /onboarding/tasks/{taskId}/delegate | TaskService.delegateTask → resolveTask 回流 owner | taskId + 被委托人 | 征询意见性质，决定权保留在原审批人 |
| transfer 转办 | POST /onboarding/tasks/{taskId}/transfer | TaskService.setAssignee | taskId + 新受理人 | 引擎不校验用户存在性，SDK 侧校验组织与权限 |
| urge 催办 | POST /onboarding/applications/{applyNo}/urge | 非引擎操作：写催办记录并触发通知；自动催办由非中断边界定时器承担 | applyNo + 节点 + 催办日期 | 同一节点每日频控一次 |
| queryProgress 进度查询 | GET /onboarding/applications/{applyNo}/progress | 只读：查业务层待办宽表，必要时回查引擎历史表 | —（只读天然幂等） | 走 CQRS 读模型，不穿透引擎运行时表 |

表 6-1 体现两层隔离。其一，渠道与引擎隔离：八个端点覆盖准入全生命周期的人机交互面，进度查询只命中 3.3.2 节的待办宽表投影而非引擎运行时表，引擎升级、流程换版、驳回实现变化均不引起渠道改动。其二，写操作的语义分级：reject 不直接暴露 ChangeActivityStateBuilder，目标回溯与历史快照由 SDK 完成；urge 刻意不映射任何引擎 API——人工催办是业务通知而非状态变更，建模为引擎操作会污染审计语义，自动催办则由 BPMN 非中断边界定时事件承担，两者通道分离、记录合流。

#### 6.1.2 统一错误码、幂等键、操作留痕横切要求

三项横切要求由网关与拦截器对门面全部接口统一实现。

**统一错误码**采用"域 + 模块 + 序号"三段式：BIZ（业务拒绝，如资料不全、名单命中）由流程内 BPMN Error 语义产生；SYS（系统故障）与 INTEG（外部集成故障）触发告警与重试策略。引擎异常须翻译而非透传：FlowableOptimisticLockingException 映射为 409 并提示客户端重试（乐观锁冲突是正常并发信号[^85^]）；任务已被认领异常映射为 409 并刷新前端状态，天然防重复提交。

**幂等键**分两级。请求级：所有写接口要求客户端携带 Idempotency-Key 请求头，服务端以"键 + 首次结果"落库，重放返回首次结果。业务级：submit 的最终兜底是 applyNo 唯一索引——businessKey 唯一约束早在 ACT-1860（2013 年）即被移除，引擎不保证唯一[^57^]，故先查重再启动、唯一索引防并发穿透（见 3.3.1 节）；审批类操作以"taskId + 操作类型 + 操作人"为幂等键，双击与网关重发不产生第二笔审批记录。

**操作留痕**由统一拦截器实现：每次门面调用记录操作人、来源渠道、时间、请求指纹、幂等键、结果码至业务层审计流水，与第 5 章留存方案合流，满足新《反洗钱法》10 年留存要求。留痕失败不阻断主流程，但须告警并补偿补录——审计链断裂本身是合规事件。

矩阵呈现两条结构性规律。其一，调用模式由监管时限语义决定："完成前须完成"的义务（名单筛查、联网核查）为同步阻塞，决定准入 SLA 下限；"完成后的报送与归档"为异步，吸收外部系统的可用性波动。其二，权威渠道优先：企业登记信息以人民银行企业信息联网核查系统（2019-06-26 上线，四部委"总对总"建设[^115^]）为准，第三方商业数据仅作辅助，对应监管语义中法定信息与辅助手段的层级区分；各行右侧合规要点均转化为 Adapter 的强制行为，而非仅文档宣示。

#### 6.2.1 身份核验类：联网核查、人脸活体、OCR

联网核查的架构事实决定集成形态：系统由"公安部共享信息系统 + 人民银行信息转接系统"两部分组成，银行经人民银行转接层以接口方式（行内 MQ 封装）接入，公安部侧为隔离共享库、定期导入数据[^54^]。据此 Adapter 须同时实现接口方式与人工直连登录兜底通道，转接系统故障时柜面走非接口方式并回传核查凭证；且核查数据存在更新延迟，界面话术不得承诺"实时户籍数据"。核查四要素与报文留档要求已列入表 6-2，不复述[^54^]。

人脸识别的三项硬约束（单独同意、不得作为唯一验证方式、10 万人备案评估）源自《人脸识别技术应用安全管理办法》（2025-06-01 施行），已列入表 6-2[^105^]；流程落地为保留"联网核查 + 人工审核"替代路径，人脸比对仅作增强手段，比对渠道优先接入国家网络身份认证公共服务（CTID 网证[^106^]）。OCR 承担证件与营业执照要素提取，授权前提与第三方 SDK 采集披露要求见表 6-2[^107^][^108^]。

#### 6.2.2 企业信息类：工商核验与受益所有人核对

对公核验主通道为企业信息联网核查系统，其级联校验语义有规章依据：按银办发〔2019〕197 号，系统依次核查手机号码、证件类型、证件号码、姓名的一致性，某一要素不一致即停止后续核查并返回结果[^110^]——该语义应建模进规则配置而非散落 Adapter 代码；手机号核查前须取得被核查人授权[^109^]，流程须在尽调节点预留授权采集动作。

受益所有人核对对接人民银行受益所有人信息管理系统（〔2024〕第 3 号令建立，2024-11-01 施行[^22^]）。〔2025〕第 12 号令第 23 条要求将自主识别结果与备案信息"查询核对"[^41^]，但备案信息仅是核实来源之一，监管明确禁止仅以查询系统或批量化、自动化手段代替必要的风险判断[^111^]。集成设计因此是"比对"而非"取值"：Adapter 返回的备案信息与 4.2 节穿透计算结果逐项比对，不一致触发差异核实分支，查询结果永不直接作为准入结论。

#### 6.2.3 名单筛查：实时阻塞、人工甄别、当日上报、三年回溯

名单筛查引擎须接入五类监控名单（涉恐名单、联合国制裁决议名单、其他获承认的国际/境外名单、人民银行要求关注名单、本行自主监测名单），依据为银反洗发〔2018〕19 号第 48 条[^29^]。集成形态由第 49、50 条时限语义导出：准入节点同步实时筛查，精准匹配自动识别、模糊匹配初筛后转人工甄别；确认命中当日上报并可停止开户；名单库调整时触发对存量客户及上溯三年交易的异步批量回溯[^29^]。接口侧的对应要求：筛查请求须携带客户全要素与名单版本号留档，使"筛查时点的名单状态"可重现。

#### 6.2.4 行内系统：核心开户、ECM 影像、电子签约

核心开户经 ESB 同步调用、MQ 异步回执[^116^]，幂等键、核心侧唯一索引与超时自动冲正要点已列入表 6-2[^49^][^50^][^113^]。此处补充两条时限纪律：隔日差错走红蓝字冲正或调账须有查明事实为依据[^117^]；跨系统最终一致由对账作业扫描超时流水兜底[^118^]。熔断纪律不可通融：资金类接口熔断时不得放行降级，宁可返回失败也不制造重复入账风险[^49^]。

ECM 影像归档的合规基准是《会计档案管理办法》（79 号令）第八条六项条件，满足后方可仅以电子形式归档；外部接收的电子凭证另须附合规电子签名（第九条）[^103^]，财会〔2020〕6 号进一步明确不得仅以纸质打印件入账归档[^104^]。"流水号 ↔ 影像索引"关联模式与人工勾对补录队列见表 6-2[^100^]。

电子签约对接 CFCA 等持牌 CA，法律依据为《电子签名法》第 14 条同等效力、第 13 条四要件与第 16 条第三方认证[^119^]；开户协议不在第三条除外情形之列，可全程电子化。技术要点为场景证书模式（一次一签、签毕即销毁）配套可信时间戳，签署证据链与流程实例绑定存档[^114^]。

### 6.3 集成可靠性模式

#### 6.3.1 Adapter 统一横切与异步任务失败处置

全部 Adapter 共享同一横切层：统一超时（按系统 SLA 分级配置）、熔断（资金类例外，见 6.2.4）、报文留档（请求/响应全文关联 applyNo 落业务层，随审计流水 10 年留存）。Adapter 只做协议适配与留档，不含分支判断（3.2.1 节红线）。

流程侧调用一律建模为异步 ServiceTask（`flowable:async="true"`），失败处置链有明确引擎语义：async job 失败后转为带冷却时间的 timer job，到期重新成为 async job 重试，重试耗尽（默认 3 次）移入 ACT_RU_DEADLETTER_JOB 死信表、不再自动执行[^51^]。瞬时故障用 `flowable:failedJobRetryTimeCycle="R3/PT10M"` 在元素级定制退避重试（Flowable 侧证据为源码级分析[^120^]，语义与 Camunda 官方文档交叉印证[^121^]），前提是下游接口幂等。死信不是自动恢复机制：须建设死信监控与人工干预队列，运维确认后经 ManagementService.moveDeadLetterJobToExecutableJob 重放并指定重试次数[^51^]；数据校验类失败不应重试而应直接转人工。技术异常（超时、宕机）与业务拒绝（核查不通过）严格分流——后者建模为 BPMN Error 边界事件走业务分支，BPMN Error 与 Java 异常在引擎语义中无任何关系[^85^]。

#### 6.3.2 Outbox 最终一致、Saga 补偿与消费端幂等

独立部署放弃本地事务后（3.1.1 节已决策），"流程状态变更 + 消息发送"的双写一致性由 Transactional Outbox 保证：事件记录与业务数据在同一本地事务写入 outbox 表，再由转发器投递 MQ，换取最终一致而不依赖 XA 与参与者同步可用[^48^]。消息可能重投，消费端必须幂等——以唯一消息 ID + 已处理日志表判重[^48^]，与门面侧幂等键构成端到端幂等链。

跨系统长事务的回滚语义由 Saga 补偿表达：核心开户等已成功活动挂 BPMN 补偿边界事件，后续节点失败时触发冲正类反向动作；引擎机制上，补偿订阅在活动**成功完成后**才注册，流程正常结束时订阅移除[^85^]，保证补偿只针对"已成功且需回滚"的步骤。四项工程纪律据此成文并纳入代码评审清单：资金相关表 append-only、错账只用冲正；外部调用必须带幂等键且键有效期覆盖业务 SLA；异步通知按"收到即 ACK、处理走本地事件"两段式保证重放安全；跨系统流程必须有补偿分支，不能只写正向[^122^]。

## 7. 关键实现模式与代码骨架

本章把第 4 章的操作映射表（表 4-3）落成可编译级代码骨架，回答四个工程问题：封装分层如何划分（7.1）、操作 SDK 如何吸收引擎边界问题（7.2）、全局事件监听如何承载审计与待办宽表（7.3）、策略与 DMN 如何接线（7.4），最后给出 Spring Boot 集成配置基线（7.5）。所有骨架以 Flowable 8.0.0（2026 年 2 月发布）为版本基线[^77^]，跨版本 API 注明引入版本；骨架中每处补偿逻辑均对应表 4-3 已识别的一个"坑"，注释中标注来源。

### 7.1 工程结构与封装分层

#### 7.1.1 模块划分与依赖方向

准入流程平台按六个 Maven 模块组织，依赖方向单向：api → facade → process-sdk → domain，adapter 仅被流程服务装配层引用。

表 7-1 模块职责与依赖边界表

| 模块 | 职责 | 允许依赖 | 禁止事项 |
|---|---|---|---|
| onboarding-api | 语义化接口与 DTO（驳回、加签、待办查询契约） | 无引擎依赖 | 不暴露 org.flowable 包类型 |
| onboarding-facade | REST/RPC 门面、鉴权、幂等判重、参数校验 | api、domain | 不直接调用引擎 Service |
| onboarding-process-sdk | 驳回/会签/加签/转办/委派/催办封装，事件监听，计票器 | 引擎 API、domain | 不含业务状态判断 |
| onboarding-domain | 申请单、审计流水、待办宽表、组织权限校验 | 无引擎依赖 | 不感知 execution/task 结构 |
| onboarding-adapter | 外部渠道适配（联网核查、短信/邮件通知、名单筛查接口）与调用幂等封装 | api、domain | 不直接操作引擎状态，不内嵌业务规则 |
| onboarding-starter | 引擎配置、Async Executor、监听器注册、Adapter 装配 | 全部模块 | 不含业务代码 |

该划分直接落实两条防线。其一，**引擎类型不外泄**：api 模块不依赖 flowable-engine，渠道与业务方只见语义接口——引擎提供的是运行时状态变更原语而非预设审批服务[^123^]，目标可达性校验、并行收拢、计票语义全部内聚在 process-sdk 一处演进，避免各业务线各自实现导致行为不一致（Insight 3）。其二，**监听器 Bean 化**：BPMN 中一律用 `flowable:delegateExpression="${voteCounter}"` 引用 Spring Bean，不用 `flowable:class`——class 方式下委托实例在部署期创建、跨流程实例共享且游离于容器外，无法注入审计 DAO 与配置[^124^]；delegateExpression 使监听器获得依赖注入与统一的生命周期管理，代价是 Bean 同样被多实例并发调用，成员字段禁止保存状态。

模块划分还直接决定测试策略：引擎边界行为集中在 process-sdk 一处，集成测试矩阵也在此收口——驳回×并行网关×CallActivity 子流程的组合场景、会签一票否决与按比例提前结束、加签后 nrOfInstances 分母变化，全部以真实引擎加 H2/目标库双环境跑通为准入门槛，而非逐业务线回归。这是"SDK 作为平台核心资产"在质量层面的兑现：碎片化的引擎能力被收敛为一次性验证过的封装，后续监管调整只改 DMN 与配置，SDK 行为保持稳定（Insight 3）。

### 7.2 流程操作 SDK

#### 7.2.1 驳回服务骨架：收拢、清理与子流程历史保护

驳回是坑密度最高的操作，SDK 按"定位—快照—迁移—清理"四步封装。定位阶段沿 BpmnModel 流入顺序流回溯确定上一人工节点——官方论坛核心开发者确认的正规做法，executionId 在每次 changeState 后重建、不可用于轨迹追踪[^88^]；引擎本身不校验目标可达性，顺序流的条件逻辑不被强制执行[^87^]，故目标合法性（排除网关、服务任务、并行域外节点）由 SDK 校验。骨架如下。

```java
package com.bank.onboarding.process.sdk.reject;

import org.flowable.bpmn.model.BpmnModel;
import org.flowable.bpmn.model.FlowElement;
import org.flowable.bpmn.model.UserTask;
import org.flowable.engine.HistoryService;
import org.flowable.engine.RepositoryService;
import org.flowable.engine.RuntimeService;
import org.flowable.engine.runtime.ChangeActivityStateBuilder;
import org.flowable.task.service.impl.persistence.entity.TaskEntity;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.List;

/**
 * 驳回服务：对应表 4-3"驳回/并行段驳回/子流程驳回"三行。
 * 完整 move* API 自 Flowable 6.3.0 进入正式版（非社区流传的 6.4.0）[^86^]。
 */
@Service
public class RejectService {

    private final RuntimeService runtimeService;
    private final RepositoryService repositoryService;
    private final HistoryService historyService;
    private final AuditTrailWriter auditTrailWriter; // domain 模块：驳回前历史快照

    // 构造器注入略
    public RejectService(RuntimeService runtimeService, RepositoryService repositoryService,
                         HistoryService historyService, AuditTrailWriter auditTrailWriter) {
        this.runtimeService = runtimeService;
        this.repositoryService = repositoryService;
        this.historyService = historyService;
        this.auditTrailWriter = auditTrailWriter;
    }

    /**
     * 驳回到上一人工节点。
     * 步骤：1) 回溯定位目标 2) 校验目标合法性（引擎不做可达性校验[^87^]）
     *       3) 并行域内则收拢全部 execution 4) 迁移并清理残留变量。
     */
    @Transactional
    public void rejectToPrevious(String taskId, String operatorId, String reason) {
        TaskEntity task = (TaskEntity) findTask(taskId); // 查当前任务，略
        BpmnModel bpmnModel = repositoryService.getBpmnModel(task.getProcessDefinitionId());

        // 1) 沿流入顺序流回溯，跳过网关/服务任务，定位上一 UserTask[^88^]
        String targetActivityId = traceBackToPreviousUserTask(bpmnModel, task.getTaskDefinitionKey());
        FlowElement target = bpmnModel.getFlowElement(targetActivityId);
        if (!(target instanceof UserTask)) {
            throw new IllegalStateException("驳回目标必须是人工节点: " + targetActivityId);
        }

        // 2) 子流程历史保护：从 CallActivity 跳回父流程时，引擎硬编码删除子流程历史
        //    （DefaultDynamicStateManager#safeDeleteSubProcessInstance 的 deleteHistory 参数）[^90^]，
        //    必须先快照留痕再迁移，监管取证要求此步不可省略。
        auditTrailWriter.snapshotBeforeReject(task.getProcessInstanceId(), taskId, operatorId, reason);

        // 3) 并行域识别与收拢：只退单分支会产生垃圾数据、join 不再等待其余分支[^89^]
        ChangeActivityStateBuilder builder = runtimeService.createChangeActivityStateBuilder()
                .processInstanceId(task.getProcessInstanceId())
                .processVariable("rejectReason", reason)
                .processVariable("rejectOperator", operatorId);
        List<String> scopeExecutionIds = parallelScopeExecutionIds(task); // 查同并行域全部 execution，略
        if (scopeExecutionIds.size() > 1) {
            builder.moveExecutionsToSingleActivityId(scopeExecutionIds, targetActivityId); // 6.3.0+
        } else if (isInsideCallActivity(task)) {
            builder.moveActivityIdToParentActivityId(task.getTaskDefinitionKey(), targetActivityId); // 6.3.0+
        } else {
            builder.moveActivityIdTo(task.getTaskDefinitionKey(), targetActivityId); // 6.3.0+
        }
        builder.changeState();

        // 4) 清理：驳回后目标节点创建全新任务实例，assignee 按定义重新解析；
        //    任务级局部变量随任务删除丢失，残留的临时变量在此按白名单清除。
        //    若需指定原办理人续办，6.6.0+ 可用 newAssigneeId 重载[^93^]。
        runtimeService.removeVariables(task.getProcessInstanceId(), List.of("tempVerifyResult", "tempScreenHint"));
    }

    private String traceBackToPreviousUserTask(BpmnModel model, String currentActivityId) {
        // 遍历 currentActivityId 的 incomingFlows，递归跳过 Gateway/ServiceTask，返回首个 UserTask id；
        // 循环驳回场景须排除"当前节点之后"的历史节点，仅以模型拓扑为准[^125^]。
        throw new UnsupportedOperationException("实现略");
    }

    // findTask / parallelScopeExecutionIds / isInsideCallActivity 实现略
}
```

骨架中有三个决策须说明。第一，驳回方法整体置于 Spring 事务内：嵌入式部署下引擎与业务共用 DataSource 与事务管理器，快照写入与 changeState 同生共死[^46^]，避免"已迁移但快照丢失"的审计缺口——独立部署形态下快照改经 Outbox 落库（3.1 节）。第二，并行收拢用 execution 而非 activityId 作迁移范围：`moveExecutionsToSingleActivityId` 显式列出同并行域全部 execution id，语义比按 activityId 匹配更精确，多实例残余执行也在此一并处理。第三，驳回目标节点列表不回查历史活动实例生成：历史轨迹在"驳回→再提交→再驳回"循环下会把当前节点之后的节点错误列为可退目标，须以 BpmnModel 拓扑回溯为准[^125^]。

#### 7.2.2 加签/转办/委派/会签计票骨架与语义校验

其余操作的引擎 API 均为单行调用，SDK 的价值在**前置语义校验与副作用补偿**：转办前校验目标用户存在性与组织权限（引擎不校验用户是否存在[^92^]）；加签只覆盖"当前多实例节点加人"，前/后加签建模为子轮次（4.4 节）；会签计票自定义——内置变量计"完成数"非"同意数"[^85^]。

```java
package com.bank.onboarding.process.sdk.ops;

import org.flowable.common.engine.api.delegate.Expression;
import org.flowable.engine.RuntimeService;
import org.flowable.engine.TaskService;
import org.flowable.engine.delegate.DelegateExecution;
import org.flowable.task.service.delegate.TaskListener;
import org.flowable.task.service.delegate.DelegateTask;
import org.springframework.stereotype.Component;
import org.springframework.stereotype.Service;

import java.util.Map;

/** 审批操作服务：转办/委派/加签/减签。全部方法先校验后调用，校验失败抛业务异常。 */
@Service
public class ApprovalOpsService {

    private final TaskService taskService;
    private final RuntimeService runtimeService;
    private final OrgPermissionChecker orgChecker; // domain 模块：用户存在性+机构权限

    public ApprovalOpsService(TaskService taskService, RuntimeService runtimeService,
                              OrgPermissionChecker orgChecker) {
        this.taskService = taskService;
        this.runtimeService = runtimeService;
        this.orgChecker = orgChecker;
    }

    /** 转办：彻底改派不回流。引擎不校验用户存在[^92^]，SDK 侧补齐校验并写审计。 */
    public void transfer(String taskId, String fromUser, String toUser, String reason) {
        orgChecker.checkAssignable(toUser, taskId); // 用户存在 + 机构权限 + 回避规则
        taskService.setAssignee(taskId, toUser);    // 同步创建 PARTICIPANT 身份链
        audit("TRANSFER", taskId, fromUser, toUser, reason);
    }

    /** 委派：征询意见，决定权保留。PENDING 期由被委派人 resolveTask 回流 owner，再由 owner complete[^92^]。 */
    public void delegate(String taskId, String toUser) {
        orgChecker.checkAssignable(toUser, taskId);
        taskService.delegateTask(taskId, toUser);   // delegationState=PENDING，owner=原办理人
    }

    /** 运行中加签：仅适用当前多实例节点；REST 无对应端点[^91^]。参数为 activityId+父执行 id，非 taskId。 */
    public void addSign(String multiInstanceActivityId, String parentExecutionId, String assignee) {
        runtimeService.addMultiInstanceExecution(multiInstanceActivityId, parentExecutionId,
                Map.<String, Object>of("assignee", assignee)); // 第三参为 Map<String, Object>，显式定界避免类型推断失配；新实例局部变量携带办理人
        // 串行多实例加签只建执行不立即生成任务（排队），调用方须知悉该差异。
    }

    /** 减签：executionIsCompleted 决定是否计入已完成分母，须按原因区分——
     *  "撤销误加签"传 false（不计票），"人员离职视为已阅"传 true；不得随意固定[^56^]。 */
    public void removeSign(String executionId, boolean countAsCompleted, String reason) {
        runtimeService.deleteMultiInstanceExecution(executionId, countAsCompleted);
        audit("REMOVE_SIGN", executionId, null, null, reason);
    }

    private void audit(String op, String refId, String from, String to, String reason) { /* 写审计流水，略 */ }
}

/** 会签计票器：complete 事件累计同意/拒绝数，completionCondition 调 shouldEnd 判断结束时机。
 *  内置 nrOfCompletedInstances 表达"全员处理完毕"而非"全员同意"，拒绝也算完成[^85^]。 */
@Component("voteCounter")
public class VoteCounter implements TaskListener {

    @Override
    public void notify(DelegateTask delegateTask) {
        if (!EVENTNAME_COMPLETE.equals(delegateTask.getEventName())) {
            return; // 只处理 complete；assignment 先于 create 触发，勿在此计票
        }
        DelegateExecution miRoot = delegateTask.getExecution().getParent(); // 多实例父执行
        boolean approved = Boolean.TRUE.equals(delegateTask.getVariableLocal("approved"));
        String key = approved ? "approvedCount" : "rejectedCount";
        int count = getLocalInt(miRoot, key) + 1; // getVariableLocal 无三参默认值重载，复用 null 安全读取
        miRoot.setVariableLocal(key, count);
    }

    /** completionCondition 引用：${voteCounter.shouldEnd(execution)}。
     *  一票否决（rejectedCount>=1）即提前结束；剩余任务被引擎删除，审计不得记为"同意"[^85^]。 */
    public boolean shouldEnd(DelegateExecution execution) {
        int rejected = getLocalInt(execution, "rejectedCount");
        int approved = getLocalInt(execution, "approvedCount");
        int total = getLocalInt(execution, "nrOfInstances");
        return rejected >= 1 || approved + rejected >= total;
    }

    private int getLocalInt(DelegateExecution e, String key) {
        Object v = e.getVariableLocal(key);
        return v == null ? 0 : ((Number) v).intValue();
    }
}
```

计票器有两个实现要点。其一，计票变量写多实例父执行的**局部变量**而非流程实例变量：嵌套会签（EDD 高管会签内再套合规复核）时互不污染；completionCondition 表达式 `${voteCounter.shouldEnd(execution)}` 在每个实例结束时求值，为 true 时剩余实例被销毁[^85^]。其二，通过/拒绝方向不由 completionCondition 表达，由后续排他网关读 approvedCount/rejectedCount 路由——计票只解决"何时结束"，表决结论必须落显式变量供审计复核[^94^]。

催办的实现形态与上述操作有本质差异：**催办不调用任何引擎状态变更 API**，本质是定时边界事件到期后的"查询 + 通知"（4.4 节），触发延迟取决于 Async Executor 轮询间隔（10 秒量级，见 7.5）。SDK 侧仅需封装到期任务查询与通知适配，骨架如下。

```java
package com.bank.onboarding.process.sdk.urge;

import org.flowable.engine.TaskService;
import org.flowable.task.api.Task;
import org.springframework.stereotype.Component;

import java.util.List;

/** 催办服务：由定时边界事件流转的 ServiceTask（delegateExpression="${urgeService}"）触发。
 *  不操作引擎状态，只做"查在办任务 + 发通知"；通知走 Adapter，渠道失败不影响流程推进。 */
@Component("urgeService")
public class UrgeService {

    private final TaskService taskService;
    private final NotificationAdapter notificationAdapter; // adapter 模块：短信/站内信/邮件

    public UrgeService(TaskService taskService, NotificationAdapter notificationAdapter) {
        this.taskService = taskService;
        this.notificationAdapter = notificationAdapter;
    }

    /** 催办轮次由流程变量 urgeRound 传入，幂等键 = taskId + 轮次，防同轮次重发。 */
    public void urge(String processInstanceId, int urgeRound) {
        List<Task> openTasks = taskService.createTaskQuery()
                .processInstanceId(processInstanceId)
                .active()
                .list();
        for (Task task : openTasks) {
            notificationAdapter.sendUrge(task, urgeRound); // 幂等键约束在 Adapter 内实现
        }
    }
}
```

骨架中通知发送刻意做成"尽力而为"：催办属提醒性质而非状态事实，重复催办的代价远低于流程停滞，故不占用引擎重试/死信体系，幂等键仅约束同轮次重发；若 SLA 超时须升级处理（换人/上收），那已是状态变更，应回到驳回/转办的 SDK 路径而非在催办中夹带。

### 7.3 全局事件监听与审计

#### 7.3.1 监听器骨架：提交后触发、失败不回滚引擎

全局监听器承担三件事：写审计流水表（t_audit_trail）、同步申请单状态、刷新待办宽表（3.3.2 节 CQRS 写侧）。三条硬性约束来自引擎事实：监听器与引擎命令同事务，异常会回滚整个流程操作，故 `isFailOnException` 必须返回 false[^59^]；`getOnTransaction` 返回 COMMITTED 使逻辑在事务提交后触发，避免读到未提交状态[^126^]；监听器只对本引擎实例生效，集群各节点均须注册[^59^]。注册方式有运行时（`runtimeService.addEventListener`）与配置化（`EngineConfigurationConfigurer<SpringProcessEngineConfiguration>` 中 `setTypedEventListeners`）两种：前者重启后丢失、每次启动须重新执行，本骨架采用此方式并以 ApplicationReadyEvent 保证重注册动作必然执行；后者在引擎创建期装配、不依赖后置动作，多节点部署建议以配置化注册为生产基线（7.5 节）。

```java
package com.bank.onboarding.process.sdk.audit;

import org.flowable.common.engine.api.delegate.event.FlowableEngineEventType;
import org.flowable.common.engine.api.delegate.event.FlowableEntityEvent;
import org.flowable.common.engine.api.delegate.event.FlowableEvent;
import org.flowable.common.engine.api.delegate.event.FlowableEventListener;
import org.flowable.engine.RuntimeService;
import org.flowable.task.service.impl.persistence.entity.TaskEntity;
import org.springframework.boot.context.event.ApplicationReadyEvent;
import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Component;

/** 全局审计监听器：TASK_CREATED/ASSIGNED/COMPLETED、PROCESS_COMPLETED 四类事件驱动审计+宽表刷新。 */
@Component
public class OnboardingAuditEventListener implements FlowableEventListener {

    private final RuntimeService runtimeService;
    private final AuditTrailWriter auditTrailWriter;   // 写 t_audit_trail
    private final TodoWideTableRefresher todoRefresher; // 刷新待办宽表
    private final ApplicationStatusSynchronizer statusSynchronizer; // 同步申请单状态

    public OnboardingAuditEventListener(RuntimeService runtimeService, AuditTrailWriter auditTrailWriter,
                                        TodoWideTableRefresher todoRefresher,
                                        ApplicationStatusSynchronizer statusSynchronizer) {
        this.runtimeService = runtimeService;
        this.auditTrailWriter = auditTrailWriter;
        this.todoRefresher = todoRefresher;
        this.statusSynchronizer = statusSynchronizer;
    }

    /** 注册时机：引擎未初始化前（ContextRefreshedEvent 阶段）注入不到 RuntimeService，
     *  须在 ApplicationReadyEvent 后置注册[^127^]。运行时注册重启丢失、每次启动须重新执行，
     *  本方法即承担该重注册职责；生产基线可改为 EngineConfigurationConfigurer.setTypedEventListeners 配置化注册。 */
    @EventListener(ApplicationReadyEvent.class)
    public void register() {
        runtimeService.addEventListener(this,
                FlowableEngineEventType.TASK_CREATED,       // 先于 TaskListener create 派发[^58^]
                FlowableEngineEventType.TASK_ASSIGNED,      // 转办（setAssignee）触发 TASK_ASSIGNED，宽表办理人列据此刷新
                FlowableEngineEventType.TASK_COMPLETED,     // 任务实体删除前、流程推进前派发
                FlowableEngineEventType.PROCESS_COMPLETED);
    }

    @Override
    public void onEvent(FlowableEvent event) {
        // 本方法在事务 COMMITTED 后触发；仍须防御性捕获——failOnException=false 只是不牵连引擎。
        try {
            FlowableEntityEvent entityEvent = (FlowableEntityEvent) event;
            if (entityEvent.getEntity() instanceof TaskEntity task) {
                switch ((FlowableEngineEventType) event.getType()) {
                    case TASK_CREATED -> {
                        auditTrailWriter.recordTaskCreated(task);
                        todoRefresher.insertTodo(task);        // 宽表插入任务快照
                    }
                    case TASK_ASSIGNED -> {
                        // 转办（setAssignee）触发 TASK_ASSIGNED，宽表办理人列据此刷新
                        todoRefresher.refreshAssignee(task.getId(), task.getAssignee());
                    }
                    case TASK_COMPLETED -> {
                        auditTrailWriter.recordTaskCompleted(task);
                        todoRefresher.closeTodo(task.getId()); // 宽表关闭待办，转已办
                    }
                    default -> { /* 其余类型不处理 */ }
                }
            } else if (event.getType() == FlowableEngineEventType.PROCESS_COMPLETED) {
                statusSynchronizer.onProcessCompleted(event.getProcessInstanceId());
            }
        } catch (RuntimeException e) {
            // 记告警日志+指标，绝不向上抛：监听器异常不得回滚引擎事务[^59^]
            AuditAlarm.raise("audit-listener-failed", event.getType().name(), e);
        }
    }

    /** 非业务关键逻辑返回 false：true 时异常上抛、当前命令失败、事务回滚[^59^]。 */
    @Override
    public boolean isFailOnException() {
        return false;
    }

    /** 提交后触发：避免监听逻辑读到未提交数据，也避免长事务内做宽表写。 */
    @Override
    public boolean isFireOnTransactionLifecycleEvent() {
        return true;
    }

    @Override
    public String getOnTransaction() {
        // 返回值为 String，官方示例两种写法皆有；TransactionState 枚举位于 impl 包
        // （org.flowable.common.engine.impl.cfg），SDK 边界不依赖 impl，直接返回字面量。
        // 支持 COMMITTED/ROLLED_BACK/COMMITTING/ROLLINGBACK。
        return "COMMITTED";
    }
}
```

骨架的一个边界须写明：审计流水落库失败时引擎流程不受影响，这是用 isFailOnException=false 换来的隔离性，代价是审计表与引擎历史可能短暂不一致——故宽表与审计表均配独立的对账作业，以引擎历史表（audit 级别）为准源补齐差异，不反向依赖监听器百分百成功。若某条审计写入被认定为关键路径（如名单命中上报），则不该走监听器，应建模为流程内显式 ServiceTask 进入重试/死信体系（4.2 节）。

事件选型还有两个工程事实影响骨架形态。其一，事件派发顺序为全局 TASK_CREATED → TaskListener assignment → create，宽表插入若依赖动态分配的办理人（create 事件 TaskListener 计算的候选组），须在监听器内延迟到提交后读取任务实体终态，而非取用事件载荷中的瞬时快照——本骨架选 COMMITTED 触发恰好规避此序问题[^58^]。其二，HISTORIC_ACTIVITY_INSTANCE_ENDED 等历史事件要求 history level ≥ activity 才派发；本设计监听运行时 TASK_* 事件而非 HISTORIC_* 事件，与 history-level=audit 基线解耦——即使后续为降负载下调历史级别，宽表链路不受影响[^58^]。

### 7.4 策略与规则

#### 7.4.1 客户类型策略与 DMN 调用接线

准入入口按客户类型路由到不同主流程定义与清单模板，差异点收敛到 `OnboardingStrategy` 接口，对公/零售各一实现，策略选择因子即申请单上的 customerType。

表 7-2 OnboardingStrategy 策略映射表

| 客户类型 | 流程定义 key | 清单决策表 | 评级决策表 | 独有环节 |
|---|---|---|---|---|
| CORP（企业/个体） | onboarding-corp | dmn-doc-checklist(CORP) | dmn-risk-rating | UBO 穿透、意愿核实、EDD 上收 |
| RETAIL（自然人） | onboarding-retail | dmn-doc-checklist(RETAIL) | dmn-risk-rating | 九要素校验、I/II/III 类户规则 |

策略层只做选择不做规则：清单内容与评级阈值全部在 DMN 内，由合规岗维护、按 key 部署即升版、执行默认取最新版本[^80^]，策略代码不因监管细则调整而变更——这与第 4 章"只改表不改图"的机制基础一致。流程内评级走 `flowable:type="dmn"` 决策任务；策略层在受理阶段需预出清单时直接调 DMN Java API：`dmnDecisionService.createExecuteDecisionBuilder().decisionKey("dmn-doc-checklist").variable("customerType", type).executeWithSingleResult()`[^128^]；该服务接口在 7.x 已由 `DmnRuleService` 更名为 `org.flowable.dmn.api.DmnDecisionService`，6.x 升级项目须全局替换注入类型（`createExecuteDecisionBuilder().decisionKey().variable().executeWithSingleResult()` 方法链本身不变）。每次决策的输入输出快照由引擎落入 ACT_DMN_HI_DECISION_EXECUTION，满足评级依据可重现的取证要求[^82^]；表达式语言为 JUEL 而非 FEEL，决策表建模工具链须按此约束选型[^79^]。

策略接口的实现须抵抗两类膨胀。第一类是"策略内嵌规则"：把评级阈值、清单条目写进策略实现类，看似减少一次 DMN 调用，实则把监管规则从合规岗可维护的决策表偷渡回代码，违背 Insight 1 的换版前提；评审时以"策略实现类出现魔法数字即驳回"为卡口。第二类是"策略按渠道细分"：柜面与 APP 的差异属接入层职责，客户类型才是准入规则的分界维度，策略键只允许取 customerType，渠道差异经 facade 层参数透传处理。受理阶段预出清单的 DMN 直调须与流程内决策任务共用同一份输入装配逻辑（同一 Assembler 类），否则预填清单与流程内正式清单可能出现版本漂移——两者按 key 执行都取最新版[^80^]，但输入变量命名不一致足以造成输出分叉。

### 7.5 Spring Boot 集成配置要点

#### 7.5.1 starter 选型与关键参数

starter 按"最小引入"原则选型：准入流程服务只需流程引擎与 DMN，引入 `flowable-spring-boot-starter-process` + `flowable-spring-boot-starter-dmn`；全量 `flowable-spring-boot-starter` 会连带启动 CMMN/IDM/事件注册引擎并建相应库表，属无谓攻击面[^62^]。8.0.0 基线为 Spring Boot 4 / Spring 7 / Jackson 3，不再支持 Spring Boot 3[^4^]，工程脚手架须按此对齐。关键配置如下。

```yaml
flowable:
  check-process-definitions: true          # classpath:/processes/ 下模型自动部署[^62^]
  database-schema-update: false            # 生产关闭自动建表，改 DBA 审核的版本化脚本（3.4.2 节）
  history-level: audit                     # audit 覆盖"谁/何时/何任务/提交了什么表单"；full 级最慢[^53^]
  process:
    async-executor-activate: true          # 默认 false，不开则全部定时器/催办失效[^62^]
    enable-safe-xml: true                  # 默认 true；CVE-2026-91197（XXE，≤8.0.0，CVSS 7.1）修复版发布前不得关闭[^18^]
    async:
      executor:
        # 以下为 6.7.0+ Global Acquire Lock 代际官方推荐值[^60^]，勿与 6.0–6.6 旧默认表混用[^61^]
        max-async-jobs-due-per-acquisition: 512   # 单次抢占批量
        timer-lock-time: PT1H                     # 定时作业锁租约 1 小时；8.0 为 Duration 写法，*-in-millis 仅为兼容 setter
        async-job-lock-time: PT1H
        default-async-job-acquire-wait-time: PT10S # 无作业时轮询间隔，决定定时器触发延迟量级
        # 注意：作业执行线程池在 starter YAML 无对应属性（开源 AsyncJobExecutorConfiguration 无线程池字段，
        # thread.core-pool-size 等写法会被静默忽略），须自定义 ThreadPoolTaskExecutor Bean 经
        # EngineConfigurationConfigurer 注入，见本节正文其三。
management:
  endpoints:
    web:
      exposure:
        include: flowable,health,metrics    # Actuator 端点 /actuator/flowable 需显式暴露[^62^]
```

三个参数决策需要论证而非照抄默认值。其一，`async-executor-activate` 默认 false 是"引擎不替你决定生产拓扑"的设计，但准入系统的催办、SLA 超时升级、备案当日预警全部建立在定时器上，故生产必须显式开启且集群至少一节点激活[^62^]。其二，acquire 等待 10 秒意味着定时器触发延迟为 10 秒量级，宕机期间到期的定时器在恢复后补执行——对外 SLA 只能承诺分钟级，第 8 章的 SLA 监控阈值按此设定[^61^]。其三，作业执行线程池不走 YAML：standalone 引擎的 `thread-pool.core-pool-size` 等配置写法不适用于 starter，开源 `AsyncJobExecutorConfiguration` 无线程池字段，`flowable.process.async.executor.thread.*` 写入会被静默忽略；线程池须以自定义 `ThreadPoolTaskExecutor` Bean（如 32/32/2048）经 `EngineConfigurationConfigurer` 注入，且扩线程池必须同步扩数据库连接池（每线程一条连接）[^60^]。队列容量与锁租约联动：作业被抢占后须在租约内执行完毕，否则被他节点重复获取，而多数作业处理器不天然幂等——核验类 Adapter 的幂等键设计（第 6 章）正是这一引擎行为的应用层兜底。高级定制（如注册配置化事件监听器、调整 MyBatis 拦截）通过暴露 `EngineConfigurationConfigurer<SpringProcessEngineConfiguration>` Bean 实现，在引擎创建前回调[^62^]，优于启动后反射修改。

`enable-safe-xml` 单列为一项基线有其现实背景：2026 年 9 月披露的 CVE-2026-91197 为 ProcessDiagramLayoutFactory 的 XXE 漏洞（CVSS 7.1，高危），影响 flowable-engine ≤ 8.0.0[^18^]。在补丁版本发布并升级完成前，本基线要求：保持 safe-xml 默认开启（对解析的 BPMN XML 施加额外检查）、模型部署入口仅对内部建模流水线开放、外部渠道提交的 XML 一律拒绝。升级补丁版本后仍需回归验证——流程模型是监管规则的载体，XML 解析面即是合规面，此项不得以"内网部署"为由降级。另须提示：`asyncHistoryEnabled` 配置自 7.0 起已移除（3.4.2 节），从 6.x 升级的项目若保留该项不会产生异步历史效果，审计链路只能依赖 7.3 节的监听器方案。

## 8. 非功能设计

本章覆盖性能容量、高可用、安全权限、信创与开源治理四条非功能轴，统一方法论：引擎官方有明确行为承诺的（锁租约、死信、历史清理默认值），以其为设计边界；官方不覆盖的（国产数据库、身份源集成），以 POC 验证与治理门禁兜底，而非假设可行。

### 8.1 性能与容量

#### 8.1.1 高频查询卸载：待办查询走宽表

待办/已办列表是最高频查询路径，实时 join 引擎运行时表与历史表既拖慢响应又令引擎主库承担分析型负载，故按 3.3.2 节的 CQRS 变体执行：写侧由全局事件监听器在事务提交后将任务快照写入业务层待办宽表，读侧只命中宽表；已办结查询直接读引擎历史表，此系官方建议用法[^53^]。宽表同时冗余受理机构列，供 8.3.1 的机构隔离过滤。

#### 8.1.2 历史表增长估算与归档窗口

引擎历史数据默认永久保存，官方明确承认这会令历史表膨胀并影响 HistoryService 性能；6.5.0 引入的 History Cleaning 默认关闭，须显式开启 `enable-history-cleaning`；开启后默认凌晨 1 点清理 365 天前已结束实例及关联数据，默认每批 100 个[^53^]。容量规划据此分两段：引擎库只保留 365 天热数据，归档衔接第 5 章三层留存，满足新《反洗钱法》10 年保存年限。估算基准：日均 2000 笔申请，平均每实例 12 个活动节点、8 个人工任务、20 个变量（audit 级持续同步）、约 7 次表单提交/明细记录。

表 8-1 历史表容量估算与清理策略表

| 表 | 增长驱动 | 年增量估算（日均 2000 笔） | 清理/归档策略 |
|---|---|---|---|
| ACT_HI_PROCINST | 每实例 1 行 | 约 73 万行 | 365 天 History Cleaning 批量删除，删前归档 |
| ACT_HI_ACTINST | 每活动节点 1 行（含重入） | 约 876 万行 | 随实例级联清理；高频轮询反模式须源头抑制 |
| ACT_HI_TASKINST | 每人工任务 1 行 | 约 584 万行 | 随实例级联清理 |
| ACT_HI_VARINST | 每实例每变量 1 行（更新为原位覆盖，不产生新行） | 约 1460 万行 | 变量只存轻量标量以压低行宽；随实例清理 |
| ACT_HI_DETAIL | 表单提交明细 | 约 500 万行 | 表单正文落业务库，本表只留属性引用 |
| ACT_GE_BYTEARRAY | 部署资源、异常堆栈、二进制变量 | 受部署频次与大变量控制 | 禁止大对象入变量；归档前校验二进制完整性 |

估算揭示两个设计含义。其一，变量表与活动表是增长主力，较实例主表高一个数量级，"变量只存轻量数据"（3.2.1 红线）因此是容量硬约束——变量更新虽为原位覆盖、不增行数，大变量仍成倍放大行宽与存储；明细表则随每次表单提交新增写入。其二，删除放大效应显著：清理一个实例需级联删除十余行关联数据，官方默认批量 100，可控制单事务锁占用与长事务风险，不应盲目调大，应以 `deleteSequentiallyUsingBatch` 分批执行，窗口安排在业务低谷[^53^]。

#### 8.1.3 定时轮询滥用导致 ACT_HI_ACTINST 爆炸的教训

官方论坛记录了一个直接对应本系统风险的案例：某流程以每分钟一次的定时器轮询外部服务状态，长周期存活实例使 ACT_HI_ACTINST 记录失控，团队最终承认"这是设计问题"并改为每小时轮询一次[^55^]。准入系统中"查询核心开户结果""跟踪备案回执"均属此类场景。设计纪律：外部状态反馈一律走 MQ 事件驱动（3.2.2），禁止在 BPMN 内建模高频轮询循环；确需轮询的周期不得低于 1 小时，并以非中断边界事件实现。

### 8.2 高可用与灾备

#### 8.2.1 集群锁机制、死信重放与滞留控制

3.4.1 节已确立"共享数据库即成集群"的拓扑，本节补充运行期纪律。防重靠行级锁加租约：作业行写入 lock owner 与锁到期时间，节点崩溃后由过期作业重置线程（默认每 60 秒扫描）释放锁供他节点接管[^61^]；6.7.0 起 Global Acquire Lock 保证同一时刻仅一个节点执行抢占查询，作业可批量获取（官方推荐单次 512 个），显著降低并发争用[^60^]。定时作业持久化于数据库，宕机期间到期的定时器在任一在线节点恢复扫描后自动执行，重启不丢[^129^]——灾备语义由此确定：RPO 取决于数据库复制，应用层无状态，重建节点即恢复执行能力。

死信不是自动恢复机制：作业默认重试 3 次耗尽后移入 ACT_RU_DEADLETTER_JOB，不再自动执行[^51^]。运维 Runbook 按官方建议分类处置——监控死信表行数告警；瞬时故障用 `ManagementService.moveDeadLetterJobToExecutableJob(jobId, retries)` 重放，批量场景用 `bulkMoveDeadLetterJobs`；delegate 代码缺陷须先修复发布再重放；无业务影响的失败可直接 `deleteDeadLetterJob`[^51^]。

滞留控制是集群调优的核心公式：已抢占作业默认须在 5 分钟锁租约内执行完毕（6.6 及以前默认；6.7.0+ 官方推荐 1 小时），队列过大会使作业滞留超时、被他节点重复抢占，而多数作业处理器不具备幂等性；扩大异步线程池必须同步扩大数据库连接池，每个后台线程都需要一条连接[^130^]。据此设定约束链：单次滞留时长 < 锁租约（生产按 6.7.0+ 代际建议置 1 小时）、线程池规模 ≤ 连接池可用连接数、核验类 Adapter 内置幂等键兜底重复执行。

### 8.3 安全与权限

#### 8.3.1 弃用引擎 IdentityService，orgPath+role 动态候选人组实现机构隔离

引擎官方明确：candidateUsers/candidateGroups 只是字符串标识，"引擎不校验提供的用户是否存在于身份组件中"[^85^]。行内用户主数据与认证授权由 4A 平台及 LDAP 承载，引擎 IdentityService/IDM 再维护一套用户组只会制造双份不一致。本设计弃用引擎身份组件：用户为 4A 工号，组为**机构路径与角色的编码组合**（格式 `ORG:{orgPath}/ROLE:{roleCode}`，如 `ORG:6100/6101/ROLE:CDD_REVIEW`）。

机构隔离由此落到候选人机制本身：审批任务不静态写死候选组，而在 TaskListener 的 create 事件中依受理机构动态计算候选组——官方推荐在分配表达式不足时以此方式动态设置候选人/候选组[^85^]。经办行任务只挂本机构组，上级复核任务挂上级机构组；查询侧以 `taskCandidateOrAssigned` 按工号检索，宽表机构冗余列再按 orgPath 前缀过滤，支行只见本机构及下辖任务，总行按权限半径见全辖。这把隔离从"查询过滤的事后遮掩"前移到"候选资格的事前限定"：不在候选组内的用户连任务存在性都不可见，且与引擎原生认领行为（claim 后他人不可办、unclaim 回候选池）兼容。

### 8.4 信创与开源治理

#### 8.4.1 国产库 POC 验证清单与 SCA/SBOM 准入

3.5 节已明确官方支持边界：开源版 databaseType 仅 {h2, mysql, oracle, postgres, mssql, db2}，企业版测试矩阵亦不含国产库，全部国产库适配均为社区补丁路线，须 POC 验证后方可投产[^59^][^64^]。社区经验将适配归纳为六层——JDBC 驱动、类型识别、SQL 方言、DDL 脚本、类型与大小写语义、回归与高可用验证；只完成前两层应用可以启动，问题往往在会签、定时任务、历史清理、版本升级时才暴露[^66^]。POC 清单据此覆盖全六层，前置为路线图第一阶段里程碑（见第 9 章）。

表 8-2 国产数据库适配 POC 验证清单

| 验证项 | 验证内容 | 通过标准 | 已知坑点依据 |
|---|---|---|---|
| 类型识别 | databaseProductName 映射至已有 databaseType | 引擎启动不报 `couldn't deduct database type` | 达梦报 "DM DBMS"、金仓报 "KingbaseES" [^131^][^72^] |
| DDL 与升级脚本 | 全套建表脚本执行与版本升级 | 生产关闭自动建表，DBA 审核版本化脚本 | GaussDB 不支持 SERIAL，须改 BIGINT+序列 [^70^] |
| Liquibase 兼容 | 事件注册等 Liquibase 管理表的变更执行 | 无 CURRENT_SCHEMA/BooleanType 报错 | 达梦须自定义 Database SPI 与 BooleanType 覆盖 [^131^] |
| 异步执行器锁 | 多节点抢占、过期锁释放、Global Acquire Lock | 无重复执行与锁泄漏 | 分布式库热点行与锁语义须实测 [^67^] |
| 大字段行为 | ACT_GE_BYTEARRAY 二进制读写与迁移 | 异常堆栈、部署资源完整无损 | TiDB 单条 KV 限制 6MB，须调参 [^75^] |
| 大小写与分页 | 表名大小写、分页与排序 SQL | 无 FlowableWrongDbException、慢 SQL 达标 | TiDB lower_case_table_names 引发版本误判 [^74^] |
| 历史清理回归 | History Cleaning 批量删除全链路 | 级联删除正确、单事务锁占用可控 | 分页与批量删除方言差异 [^66^] |
| 故障切换 | 节点宕机后作业接管与定时器补触发 | 接管延迟在锁租约+重置间隔量级内 | 过期重置默认 60 秒 [^61^] |

清单的取向是"以引擎行为为锚、而非以数据库功能为锚"：每一项对应引擎的一个可观测行为（启动、抢占、清理、切换），通过标准均可自动化断言，POC 结果可直接转化为 CI 回归套件，随版本升级持续复跑。坑点列全部来自社区实战记录，这界定了风险性质——国产库适配不存在"官方宣布支持"的终态，只有"补丁 + 持续回归"的工程常态。

开源治理方面，引入 Flowable 及其传递依赖须纳入行内开源软件全生命周期治理，参照北京农商银行实践：以 SCA 工具对源码、制品及 SBOM 做组件识别（组件构成、漏洞、许可证）；与 GitLab 对接增量扫描，与 Nexus 制品库对接在组件下载环节执行准入校验，与 DevOps 平台对接在构建、提测、发布环节拦截不合规组件，并经制品库代理衔接金融业开源技术服务平台可信中心仓[^132^]。该框架对应人民银行等五部门《关于规范金融业开源技术应用与发展的意见》的"台账、准入、监测、应急"要求[^133^]。具体含义：Flowable 版本升级、国产库补丁包及任何新增传递依赖都须重新过门禁，治理结论与 POC 回归结果共同构成投产准入条件。

## 9. 风险、反模式与实施路线图

本章收束全文：9.1 节将前八章分散的设计纪律归纳为十项可检查的反模式；9.2 节给出四类关键风险及缓解措施，每项均可回溯到前文的机制依据；9.3 节按"先验证风险、再沉淀平台、后推广业务"的次序排布四阶段实施路线图。

### 9.1 反模式清单

#### 9.1.1 十大反模式表

反模式是"引擎允许但工程上必然后悔"的用法。表 9-1 按危害类型归并十项，每项标注典型后果与本设计对应的防线，可作为代码评审与流程设计评审的检查清单。

表 9-1 十大反模式与设计防线对照表

| # | 反模式 | 典型后果 | 本设计防线 |
|---|---|---|---|
| 1 | 巨型图：一张图装全部客户类型与分支 | 网关组合爆炸、实例迁移脆弱、监管调整必改图 | 按客户类型分定义、网关分叉≤三层（4.1.2） |
| 2 | 规则硬编码进网关条件或 Java 代码 | 监管细则每次调整都改代码发版、在途迁移 | 三类规则（评级/路由/清单）外置 DMN（4.3），名单命中处置并入评级决策表首行规则（命中即拒绝） |
| 3 | 监听器中执行远程调用等重操作 | 监听器异常回滚引擎事务、主事务被拖长 | 监听器只做提交后异步写，isFailOnException=false（7.3）[^59^] |
| 4 | 流程变量存影像正文、报文等大对象 | ACT_HI_VARINST/ACT_GE_BYTEARRAY 行宽爆炸，audit 级同步写入放大 | 变量只存轻量标量与引用，正文落 ECM/业务库（5.2、8.1.2） |
| 5 | 直接 UPDATE ACT_* 表修数据 | 引擎缓存与表状态分裂，升级脚本冲突不可维护 | 状态变更一律走 API/SDK；act 表只读（7.2） |
| 6 | 待办查询实时 join 运行时表与历史表 | 高频列表压垮引擎主库，响应不可控 | CQRS 宽表读模型，历史查询走 HistoryService（3.3.2、8.1.1） |
| 7 | BPMN 内建模高频定时轮询外部状态 | ACT_HI_ACTINST 失控，官方论坛案例中团队被迫认列为设计问题 | 外部反馈走 MQ 事件驱动；轮询周期≥1 小时（8.1.3）[^55^] |
| 8 | 依赖 businessKey 唯一做幂等 | 唯一约束已被 ACT-1860 移除，重复提交产生重复实例 | 业务表自建唯一索引 + 引擎侧复合索引双防线（5.1.2）[^57^] |
| 9 | 驳回/加签绕过 SDK 直调引擎原生 API | 并行分支垃圾数据、join 失效、子流程历史被物理删除 | 操作 SDK 内置收拢、快照、计票补偿（4.4、7.2）[^89^][^90^] |
| 10 | 以 executionId 追踪轨迹、以完成数当同意数 | changeState 重建 execution 致轨迹断链；会签"拒绝也算完成" | SDK 计票器累计 approvedCount/rejectedCount；轨迹以业务审计表为准（4.4）[^88^][^85^] |

表 9-1 的十项可归纳为三类根源。第一类是**把引擎当数据库用**（#4、#5、#6、#8）：ACT 表是引擎内部表示而非业务存储，变量、查询、幂等都须在业务层重建语义。第二类是**把引擎当规则引擎用**（#1、#2）：BPMN 表达骨架、DMN 表达规则的分工一旦被破坏，监管换版的成本就从"改一张决策表"升级为"改图发版加在途迁移"。第三类是**低估运行时原语的边界**（#3、#7、#9、#10）：监听器、定时器、changeState、多实例变量都是原语而非服务，其组合语义只能由平台 SDK 统一兜底——这正是第 4、7 章将 SDK 列为核心资产的原因。

### 9.2 关键风险与缓解

#### 9.2.1 四类风险与缓解表

风险排序依据"发生概率 × 影响 × 可控性"：信创适配与开源漏洞属技术可控型，靠前置验证与治理门禁；监管细则变动与在途迁移属外部驱动型，靠架构弹性吸收。

表 9-2 关键风险与缓解措施表

| 风险 | 依据与触发场景 | 影响 | 缓解措施 |
|---|---|---|---|
| 信创数据库适配失败 | 开源版官方支持清单仅 {h2, mysql, oracle, postgres, mssql, db2}，国产库全为社区补丁路线 [^59^][^64^]；坑点各异：达梦 BooleanType、GaussDB SERIAL、TiDB 6MB KV 限制 [^131^][^70^][^75^] | 会签、定时、清理等场景运行期才暴露缺陷，投产返工 | POC 前置为路线图第一阶段，八项清单全部通过方可全面开发；POC 断言转 CI 回归套件随版本复跑（8.4.1） |
| 监管细则变动 | 11 号令 2026-01-01 施行、12 号令 2026-01-20 施行，评级维度与审批阈值随细则持续调整 [^21^][^40^] | 规则硬编码场景下每次调整须发版与在途迁移 | 三类规则外置 DMN（名单命中处置并入评级决策表首行规则），合规岗维护热更新；新规切换按"受理日期入参分流 + 双轨发布"（4.5.2） |
| 在途实例迁移受限 | 官方迁移不支持多实例执行集合整体迁移、不支持迁入多实例活动 [^97^] | 会签中的在途单无法切换新版，混版运行期监管口径不一 | 在途走旧版为原则；确需迁移先 validateMigration 预校验；多实例在途单显式登记、走旧版办结（4.5.1） |
| 开源组件漏洞与供应链 | CVE-2026-91197（XXE，CVSS 7.1）影响 flowable-engine ≤8.0.0，2026-09-14 披露 [^18^] | 恶意 BPMN XML 触发服务端文件读取，须紧急补丁 | 保持 `flowable.process.enable-safe-xml=true`；SCA/SBOM 准入门禁覆盖传递依赖，补丁版本跟踪纳入运维 Runbook（8.4.1）[^132^] |

四类风险呈共同的结构特征：**不存在"一次处置、永久免疫"的终态**。国产库适配是"补丁+持续回归"的工程常态；监管换版以年度为周期持续发生；漏洞披露随依赖演进不断出现。因此缓解措施全部落在机制而非项目上——POC 转 CI 回归、DMN 外置、SBOM 门禁——使风险应对内化为日常流程而非临时动员。

### 9.3 实施路线图

#### 9.3.1 四阶段实施路线

路线图按"风险前置、平台先行、业务跟进"排序，前一阶段的出口标准是后一阶段的准入条件：

1. **阶段一：POC 验证（约 6–8 周）**。目标是把最大不确定性在全面投入前消化掉。三项任务并行：其一，目标国产数据库适配 POC，执行表 8-2 全部八项验证（类型识别、DDL 与升级、Liquibase 兼容、异步执行器锁、大字段、大小写与分页、历史清理回归、故障切换），通过断言固化为 CI 回归套件；其二，驳回能力组合验证，以 ChangeActivityStateBuilder（6.3.0+）跑通"驳回×并行会签×子流程"矩阵，重点确认并行收拢与子流程历史删除边界 [^89^][^90^]；其三，开源治理门禁搭建，完成 Flowable 及传递依赖的 SCA/SBOM 准入与 CVE-2026-91197 补丁处置 [^132^][^18^]。出口标准：POC 清单全通过、SDK 原型矩阵全绿、门禁流水线可用。若国产库 POC 关键项不通过，则回到选型决策框架（1.2.3）重估商业 BPM 路线。
2. **阶段二：平台层建设（约 8–10 周）**。按第 7 章骨架落地四项平台资产：流程操作 SDK（驳回/加签/减签/转办/委派/催办，内置变量清理、历史快照、计票器）；全局事件监听与审计流水 t_audit_trail；对外 API 门面（渠道零感知 Flowable）与待办宽表投影；Outbox 与死信重放 Runbook。本阶段不接真实业务，以 4.2 节骨架的桩流程做集成测试。出口标准：SDK 接口冻结、审计流水通过取证演练、宽表在 2000 笔/日容量基准下压测达标。
3. **阶段三：首条流程上线（约 6–8 周）**。选择对公准入 onboarding-corp 作为首条流程——其覆盖 UBO 穿透、EDD 上收、会签等最复杂场景，验证通过即覆盖其余流程的能力超集。同步交付三张 DMN 决策表（评级/路由/清单）与三层留存归档衔接（5.3），并对接联网核查、名单筛查、核心开户、ECM 四类外部通道（6.2）。以单一分行灰度，名单命中当日上报时限作灰度观察重点。出口标准：灰度期满无 P2 以上缺陷、归档链路经合规抽检、DMN 热更新演练一次。
4. **阶段四：多渠道推广与运营移交（持续）**。零售流程 onboarding-retail 复用子流程与 SDK 上线；柜面、线上渠道分批经门面接入；规则维护职责移交合规岗，形成"监管发文→决策表新版→灰度观察→全量"闭环（4.5.2）；平台指标（待办时延、死信量、历史表增速）纳入例行运营。后续接入新业务线时，只新增流程定义与 DMN 表，平台层零改动——这是检验阶段二资产沉淀是否合格的最终标准。
